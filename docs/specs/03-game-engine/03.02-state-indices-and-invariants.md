## 2. Objetivo, alcance y valor

Proponer una representación lógica única, precisa e inmutable para Game, AI, práctica y replay. El convenio vincula pozo reglamentario, índice del array y orientación de presentación sin invertir reglas al girar la cámara. La validación distinguirá una estructura bien formada de una posición alcanzable y de una interpretación normativa aprobada.

Incluye tablero fijo, kazanes, tuzdyks, turno, versiones, revisión y contexto necesario de repetición. No define tablas SQL ni API pública completa, no implementa serializadores y no certifica edición reglamentaria. La asignación aleatoria de colores online queda fuera del motor puro; local/IA permite elegir bando según producto. Ningún cambio de cámara, idioma o identidad cambia el contenido lógico.

## 5. Invariantes y orientación

Convenio técnico `PROPUESTA`: jugador `white=0`, `black=1`; `board[player][pitIndex]`, `pitIndex=0..8` corresponde al número propio `1..9`. Ciclo fijo `white[0]…white[8]→black[0]…black[8]→white[0]`. Las filas de una vista cenital con blancas abajo aparecen como sigue:

```text
campo negro:  B8 B7 B6 B5 B4 B3 B2 B1 B0  (números propios 9…1)
campo blanco: A0 A1 A2 A3 A4 A5 A6 A7 A8  (números propios 1…9)
ciclo: A0→A1→…→A8→B0→B1→…→B8→A0
```

La proyección de vista puede rotar filas/posiciones, conservando `(player,pitIndex)` del dominio y etiqueta de número propio. No cambiar el ciclo al invertir cámara. Los kazanes no son eslabones de ese ciclo; reciben solo efectos reglamentarios. El convenio técnico representa la numeración/recorrido identificados en 03.01, sin declarar aprobado un algoritmo de final.

Invariantes:

- Cada cantidad es entero no negativo ≤162; la suma de 18 pozos y dos kazanes es exactamente 162 en estados reglamentarios. Sumar con tipo suficientemente amplio y validar antes de conversiones.
- Tuzdyk activo pertenece al jugador indicado y reside en campo rival; índice permitido 0..7, único por propietario. Si ambos existen, sus índices propios difieren. Su pozo tiene cero piedras; los depósitos incrementan el kazán propietario.
- `turn` solo es blanco o negro. El estado inicial tiene blancas, nueve piedras por pozo, kazanes cero, ningún tuzdyk y revisión cero. Elegir bando no cambia quién comienza.
- Revisión secuencial, formato, reglamento, comandos, eventos y replay son conceptos distintos. Incrementar una revisión no modifica una versión de regla.
- Un estado con 162 y campos válidos puede seguir siendo inalcanzable o tener historia incoherente. No elevar validación estructural a prueba reglamentaria.
- Un rechazo conserva estado, contexto e historial de entrada; copiar arrays no basta si existen punteros/slices/maps compartidos.

## 7. Diseño y responsabilidades

Motor Go: tipos, validación, fábrica inicial y transformaciones puras. Game: asociación participante↔color, autorización, revisión confirmada y persistencia. AI recibe el mismo estado/reglas/contexto, sin decidir participantes ni confirmar resultado. La web convierte coordenadas de presentación a referencias devueltas por Go; no calcula legalidad. DTO públicos generados en [05.02](../../index.md#spec-05-02), `PENDIENTE_LOTE_3`, se adaptan al dominio y no obligan a compartir sus interiores con cliente.

Dos validaciones propuestas: `ValidateStructure` comprueba tipos/rangos/invariantes y compatibilidad; `ValidateHistory` comprueba secuencia/origen/versiones y contexto. Ninguna hace por sí sola verificación completa de alcanzabilidad de un escenario educativo arbitrario. Datos confirmados incompatibles se bloquean para diagnóstico; nunca restar piedras o borrar tuzdyks para normalizar.

El motor construye el siguiente estado con revisión `r+1` al aceptar una jugada; Game comprueba/persiste esa revisión bajo su transacción. Una preview devuelve una revisión hipotética expresamente no confirmada. Otros comandos de aplicación pueden avanzar la revisión del agregado Game conforme a 05.03; no se presume correspondencia uno a uno entre revisión y número de siembras.

## 8. Contratos de estado, tipos y errores

Propuesta de contrato interno; la serialización final se revisará con 05.02/05.03:

| Campo | Tipo/validación y significado |
|---|---|
| `stateSchemaVersion` | Entero positivo; candidato `1`; enum de formatos soportados, no aceptar desconocido como actual. |
| `rulesVersion` | Identificador no vacío de edición/interpretación adoptada; actualmente pendiente. El marcador documental no es válido para iniciar producto. |
| `revision` | `uint64`; incremento comprobado, error ante overflow. DTO JSON propone cadena decimal para no perder precisión en JavaScript. |
| `board` | `[2][9]uint16`; entrada JSON exige dimensiones exactas y enteros 0..162 antes de convertir. |
| `kazans` | `[2]uint16`, rangos y suma total; pertenecen al mismo jugador que su índice. |
| `tuzdyks` | Dos opcionales, uno por propietario; objeto `{owner: Player, at:{player: Player,pitIndex:uint8}}` o nulo. `owner` coincide con slot y campo es rival. |
| `turn` | `Player`, enum cerrado `white\|black`; no aceptar enteros externos fuera de 0/1. |
| `terminal` | Nulo o resultado/causa tipados de 03.04; una transición sobre estado terminado se rechaza. Terminal administrativo solo se fija por Game. |
| `repetition` | Contexto de posiciones/cuentas bajo la misma regla, versión e integridad de historia; propuesta detallada en 03.04, aún bloqueada normativamente. |

La identidad de jugador del dominio es color, no ID de usuario. `gameId`, alias, sesión, commandId, timestamps, autenticación y rank eligibility pertenecen al agregado/DTO Game, no determinan si una piedra se captura. El contexto de repetición se trata como entrada lógica, sin consulta oculta a DB.

| Versión distinta | Uso |
|---|---|
| `stateSchemaVersion` | Codificación y validación del estado |
| `rulesVersion` | Reglamento e interpretaciones para legalidad |
| `commandVersion` | Forma del comando, definida en 03.03/05.02 |
| `eventSchemaVersion` | Forma de eventos semánticos, definida en 03.03 |
| `replaySchemaVersion`, `moveRecordVersion` | Contenedor y registros históricos, 03.04 |
| Identidad de build del motor | Evidencia del artefacto que aplica esas reglas; no reemplaza ninguna de las anteriores |

Errores candidatos tipados: `INVALID_STATE_SHAPE`, `INVALID_PLAYER`, `INVALID_PIT_INDEX`, `INVALID_STONE_COUNT`, `STONE_TOTAL_MISMATCH`, `INVALID_TUZDYK`, `UNSUPPORTED_STATE_VERSION`, `UNSUPPORTED_RULES_VERSION`, `REVISION_OVERFLOW`, `INCOMPLETE_REPETITION_CONTEXT`, `NORMATIVE_RULE_UNRESOLVED`. Error interno no expone secretos/volcado de sesión. HTTP/status corresponden a 05.02; paginación no aplica a un estado fijo. Idempotencia y autorización se resuelven en Game, sin map de comandos dentro del estado de piedras.

## 9. Metodología futura ordenada y justificada

1. Confirmar permiso y resolver edición/interpretaciones bloqueadas de 03.01; evita construir un estado etiquetado con regla ficticia.
2. Revisar tipos y DTO con Game/AI y acordar representación decimal de revisión; evita pérdida de precisión o campos versionados confundidos.
3. Implementar fábrica inicial y recorrido independiente de cámara; verificar 18 referencias distintas y retorno al origen tras 18 pasos.
4. Implementar validaciones de forma antes de conversiones/índices y después invariantes de dominio; evita overflow y pánicos por input.
5. Implementar clonación profunda del contexto y opcionales, conservando valor de arrays; documentar ownership de cada slice/map.
6. Implementar adaptadores de serialización y política de compatibilidad explícita; probar round-trip sin convertir desconocido a valor cero.
7. Construir propiedades/fuzzing y simulaciones solo sobre reglas/corpus revisados; distinguir generador de estados válidos de generador arbitrario negativo.
8. Integrar Game/AI con igual versión y registrar pruebas antes de aceptar conservación o replay; no sustituir fallo semántico por otra codificación.

## 10. Justificación y alternativas

Arrays fijos expresan la geometría decidida y simplifican copia por valor; el coste es adaptar DTO y mantener contexto dinámico con copia profunda. Un vector único de 18 podría representar el ciclo, pero sería un adaptador interno, sin sustituir `[2][9]` de B1. Opcionales explícitos evitan confundir ausencia de tuzdyk con primer pozo. Propietario explícito aporta validación redundante útil frente a una inferencia desde campo/cámara.

Separar revisión y versiones evita que la tercera repetición desaparezca porque cambió un contador técnico; la equivalencia exacta sigue pendiente. Revisión JSON decimal es una propuesta de interoperabilidad, no cambio de reglamento. No se añade un límite de duración o número de movimientos por resolver tamaño de historia; cualquier política de recursos que pueda terminar partidas exige evaluación y aprobación.

## 12. Casos límite, seguridad y recuperación

Rechazar negativos, fracciones, dimensiones adicionales, cantidades excesivas, enum desconocido, suma alterada y null en campos obligatorios antes de aplicar reglas. No asumir que JSON numérico cabe en `uint16` ni truncar. Array válido con tuzdyk lleno, en campo propio, noveno u homólogo invalida estado. Una revisión máxima no vuelve a cero.

Restaurar un snapshot sin contexto/historia coherentes puede permitir mostrar tablero, pero no continuar una partida oficial o aceptar reclamación como si la historia estuviera completa; recuperar registros y recalcular o bloquear de forma explícita. Recuperación local no confiere autoridad al snapshot del navegador: Game/simulación Go valida formato y reglas según [PRE-02.D3](../../decision-register.md#pre-02-d3). No inferir ranked de los datos almacenados por cliente.

Propiedades se comprueban en fronteras de movimiento, no sobre cada frame animado; la escena puede representar piedras en tránsito sin modificar el estado lógico. Datos de accesibilidad muestran índices propios, cantidades y propietarios estables; no exigir una orientación física específica para comprender turno/captura.

## 15. Observabilidad, compatibilidad y rollback

Propuesta de evidencia: versión de formato/reglas/build, revisión y código de violación, con estado sintético o minimizado cuando proceda; sin sesiones/identidades ni datos personales en logs. El motor puro devuelve información y el adaptador registra; no introduce telemetría lateral. Ningún resultado de rendimiento o conservación está medido actualmente.

Migración futura requiere transformación explícita, validación antes/después y compatibilidad de replay; formato nuevo no puede cambiar resultado. Conservar versión y snapshot original para revisión, sin crear archivos de producto ahora. Rollback usa lector/motor compatible y no decrementa revisiones confirmadas ni modifica kazanes para hacer válido un registro corrupto. Reparaciones de partidas requieren plan/autorización independientes.
