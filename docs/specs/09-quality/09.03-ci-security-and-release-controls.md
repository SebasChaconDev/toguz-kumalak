## 5. Invariantes y entidades

- Check obligatorio está ligado al HEAD exacto revisado; un verde de commit anterior o resultado cancelado/ausente no autoriza merge.
- Motor compartido modificado dispara pruebas/builds de Game y AI con la misma versión/digest, no solo paquete engine. Identity sigue autónomo.
- Ninguna rama/PR externo obtiene secretos de producción, de preview privilegiada, OIDC de despliegue o escritura del repositorio por ejecutar código no confiable.
- PostgreSQL real valida integración; simulación de SQL no se presenta como equivalente.
- Deploy no es consecuencia de pasar CI sin permiso de recursos/despliegue. Ni merge ni tag autoriza gasto.
- Evidencia PASS exige observado. SKIPPED/UNAVAILABLE/cancelled/timeout se mapean a BLOCKED/NOT_RUN con razón y bloquean requerido.
- Rollback de código no revierte migraciones/datos, no reabre refresh/grants ni borra historia/ratings.

Entidades PROPUESTA: CheckPlan/1, ModuleManifest/1, EnvironmentManifest/1, QA-Evidence/1 y ReleaseCandidate/1. No se crea un orquestador o microservicio adicional.

## 7. Diseño de gates y activadores

Las capas siguientes son PROPUESTA de ejecución futura. La duración se medirá antes de fijar presupuestos; «rápido/medio/completo» indica alcance y orden, no minutos garantizados.

| Gate / check lógico | Contenido mínimo | Evidencia |
|---|---|---|
| Rápido QA-FAST | Permiso/alcance, formato/lint/Go fmt, TS tipos, vet, unitarias puras incl14ACC, contratos/schema parseados, fixtures/semillas fuzz de regresión, secretos diff y dependencias cambiadas | ModuleManifest e informe por paquete/caso, formato/tipos/vet y scan |
| Medio QA-INTEGRATION | Build cada módulo afectado GOWORK=off y motor/Game/AI coherentes; Go test/cobertura90/80 y race, PostgreSQL real+Goose+sqlc, HTTP/contratos/modelos GoTS/eventos, F-Q1-03–14/17 afectados; Vitest/RTL y Next build; E2E críticos afectados en tres motores yHTML | QA-Evidence/1 SQL/HTTP/race/contratos, build independiente, cobertura y trazas09.02 |
| Completo QA-FULL | Regresión de rutas críticas09.01/09.02 del conjunto integrado; campañas fuzz exploratorias con semilla/duración registradas, matrices navegador/modo/idioma, visual fijo y evaluación manual aplicable, auditoría multimódulo/artefactos; comprobar compatibilidad con releases vigentes | Reporte de todas las filas requeridas, contraejemplos, baseline/revisión y matriz de compatibilidad |
| Candidato QA-RELEASE | QA-FULL del candidato exacto, benchmark09.04, restauración10.03 y migraciones compatibles/rollback10.04, revisión de licencias/privacidad/contratos/permisos, sin bloqueantes | Dossier de release con builds/componentes/contratos/datos y aceptación humana |
| Tras despliegue QA-SMOKE | Solo despliegue autorizado: comprobar identidad/protección/versiones, lectura/acción sintética permitida y reconciliación, observabilidad y ausencia de secretos; no carga destructiva | Entorno/deployment/commit, smoke por paso y decisión continuar/contener |

Módulos Go se prueban desde su go.mod con toolchain/lock/digest explícitos y GOWORK=off para detectar dependencias ocultas del workspace. Se comprueban engine y los tres servicios como módulos independientes; Game y AI deben resolver el mismo motor. Compartir Go no comparte repositorios SQL. Build local aislado tampoco demuestra empaquetado Vercel real: ese ensayo requiere permiso/entorno10.01.

| Cambio | Conjunto mínimo de impacto |
|---|---|
| Motor, reglas/estado/eventos o dependencia Go común | Engine+Game+AI,14ACC, historia/replay/TT/fallback; contratos consumidores y E2E de acciones afectadas |
| HTTP/OpenAPI/modelos/JSON Schema/JCS | Productor y todos los consumidores Go/TS, generation drift, negativos/compatibilidad S2S y eventos |
| Identity/JWKS/sesión/CSRF | Identity+Game autorización y E2E sesiones/privacidad/recuperación; no añadir engine a Identity por obligación |
| SQL/Game/Elo/migración/queries | PostgreSQL real/Goose/sqlc/locks/resultados/receipts/restart/restore y UI afectada |
| Web/3D/assets/i18n | TS/RTL/build/Playwright/HTML/accesibilidad/visual; backend contratos sigue checkeado |
| Dependencia/build/CI/seguridad | Todos los módulos o consumidores afectados y controles de cadena de suministro; revisión especial de permisos |
| Solo Markdown sin contrato/cambio de producto | Auditoría documental/autoridad/enlaces/alcance; justificar no aplicabilidad de checks producto. Cambiar especificación contractual exige revisión impacto, sin fingir implementación probada. |

### Ejecución exacta por evento futuro

| Evento | Qué se ejecuta y qué bloquea |
|---|---|
| Cada PR al abrir/sincronizar | QA-FAST y QA-INTEGRATION del impacto; QA-FULL del HEAD candidato antes de permitir merge, con rutas críticas completas pertinentes y matriz registrada. Checks requeridos no se saltan por falta de secreto/proveedor; esos casos quedan BLOCKED y se usa la contingencia autorizada. PR documental se rige por fila específica anterior. |
| Tras integración en main | Reejecutar QA-FAST/INTEGRATION/FULL sobre commit integrado para detectar diferencias de composición/merge; publicar artefactos y comparar manifest. Fallo abre incidente/regresión y bloquea release siguiente; no desplegar automáticamente. |
| Antes de cada release | QA-RELEASE completo sobre combinación exacta de componentes y schemaVersions; incluir campañas intensivas, pruebas físicas/manuales vigentes para el cambio y benchmark/restauración observados. No reutilizar prueba de otra combinación sin justificar compatibilidad e impacto. |
| Tras despliegue autorizado | QA-SMOKE del entorno real protegido con fixture/acción sintética expresamente permitidos y métricas reales; no tests destructivos/fuzz/carga en producción por inferencia. Fallo activa contención10.04, no rollback de datos automático. |

Una matriz de pruebas no afectadas puede referenciar evidencia previa solo con commit/compatibilidad y revisión explícita; no omite los checks requeridos del candidato. Cambiar un check requerido o exención es cambio de gobierno revisado, no ajuste unilateral para fusionar.

## 8. Contratos de ejecución, permisos y cadena de suministro

CheckPlan/1 contiene HEAD/base, fuentes, impacto, módulos, suites/casos/AC requeridos, capas, entornos y evidencia esperada. EnvironmentManifest/1 identifica OS/runtime/PG/generadores/browsers, límites y aislamiento, versión de migración/schema/contratos, proveedores reales/dobles y autorización. QA-Evidence/1 conserva comandos, esperado/observado/status/artefactos/hash/revisor de09.01.

PROPUESTA de comandos lógicos, a adaptar al manifiesto real sin ejecutarlos ahora: go test por módulo, go vet, go test -race donde aplique, seeds+fuzz exploratorio con presupuesto explícito, cobertura por paquete y build aislado; sqlc generate/Goose desde cero y upgrade; pnpm tipos/lint/Vitest/Next build/Playwright; generación OpenAPI/JSON Schema; govulncheck en cada módulo/consumer y auditoría del lock TS. Los nombres de scripts de producto aún no existen y no se inventan como resultados. La regeneración ocurre en workspace desechable de CI y debe dejar cero diff frente al generado versionado; no editar generado a mano para ocultar drift.

Permisos Actions por defecto de solo lectura a contenidos; ampliar por job solo si se justifica y aprueba. Fijar actions de terceros por commit revisado y toolchains/containers por versión/digest verificables; revisar actualización y procedencia. No ejecutar código de PR externo con pull_request_target/secretos o runner persistente privilegiado. Validación de PR externo sin secretos usa PostgreSQL efímero y proveedores simulados. Una revisión humana no convierte código arbitrario en confiable: integración con secretos se hace desde revisión promovida a entorno aislado explícitamente autorizado, con permisos/datos mínimos.

No compartir cache/escritura de artefactos confiables con jobs de PR externo; claves de cache incluyen versión/lock/entorno y resultados no son fuente de autoridad. No interpolar título/body de PR como shell. No exponer token por logs/comandos/artefactos, prefijos públicos Next, bundle, source maps o capturas. Escanear también artefactos compilados pertinentes, no solo diff.

Preview protegida requiere identidad del deployment y auth de aplicación separadas, credenciales sintéticas por entorno, rutas/same-origin/cookies probadas y llamada negativa sin protección/no autorizado. Bypass de automatización, si se autoriza, solo en ejecutor/servidor de acceso mínimo, nunca navegador público/URL/log. No desactivar protección para que Playwright pase. Preview no tiene producción ni permiso de migrar producción.

## 9. Metodología futura ordenada y justificada

1. Obtener permiso de implementación CI y configuración GitHub; inspeccionar automatizaciones de push/deploy antes de activarlas. Diseñar checks en PR y revisarlos como código antes de aplicación.
2. Inventariar raíces/módulos/toolchains/generadores y matriz de impacto; GOWORK=off verifica autonomía y consumidor compartido.
3. Implementar QA-FAST sin secretos y probar el propio filtro con cambios representativos; filtro incierto cae a conjunto completo.
4. Añadir PostgreSQL efímero/Goose/sqlc e integración09.01, luego web/browsers09.02; garantizar limpieza de recursos/coste por run y artefactos seguros.
5. Añadir scans por módulo/lock/diff/artefacto y permisos mínimos; probar PR externo, cache y logs sin secretos.
6. Probar un fallo deliberado controlado de check requerido y un estado ausente/cancelado: la protección debe impedir merge. No probar el control fusionando código roto.
7. Configurar main para requerir PR, revisión/checks del commit vigente y protección ante force push; verificar disponibilidad/aplicación a administradores y ninguna evasión. Si el plan no lo permite, mantener gate manual explícito y registrar falta de control, sin afirmar equivalente automatizado.
8. Conectar evidencias a09.04/10.04/11.03; despliegue requiere autorización separada. Validar smoke y recuperación sin confundir rollback de código/datos.

## 10. Justificación y alternativas

Escalonar ofrece diagnóstico temprano y conserva control completo antes de merge/release. Filtrar por impacto reduce coste, pero consumidor compartido y fallback conservador evitan huecos. Un único test desde go.work ocultaría falta de módulo en deployment; por eso cada raíz compila sola.

No se impone herramienta comercial. Estático puede usar vet más analizador abierto revisado; scans de secretos/dependencias emplean herramientas gratuitas verificadas bajo permiso futuro. Si no están disponibles en Actions/plan, ejecutar control equivalente autorizado local aislado con mismo commit/comandos/artefactos y revisión, o bloquear. Esto no sustituye un check obligatorio configurado sin actualizar previamente el gate humano correspondiente.

## 11. Ejemplo documental explicado

Plan lógico, no YAML ejecutable ni resultado de CI:

```text
PR cambia modules/engine y Game:
impacto = engine + Game + AI + contratos/eventos + web crítico
QA-FAST:14ACC/unit/format/vet/modelos/secrets
QA-INTEGRATION: tres builds Go independientes pertinentes,
PGreal+Goose+sqlc+race+CAS/receipts/Elo,Nextbuild,Playwright3motores

HEAD cambia durante revisión -> invalidar dossier anterior y volver a checks requeridos
QA-RELEASE/QA-SMOKE no se disparan como permiso automático de deploy
```

Identity conserva su módulo/checks base sin importar engine. «Tres builds pertinentes» identifica engine/Game/AI; los tres servicios Identity/Game/AI siguen teniendo verificación autónoma en el conjunto completo. Cada paso crea evidencia futura o estado bloqueado, no un PASS literal.

## 12. Fallos, límites, seguridad y contingencias

| Falta/fallo | Tratamiento futuro |
|---|---|
| Runner/browser/PG real no disponible | BLOCKED/NOT_RUN requerido; reintentar acotado con runId nuevo o ejecutar entorno equivalente autorizado, sin SQLmock/otro navegador como sustitución silenciosa. |
| Presupuesto gratuito/almacenamiento insuficiente | Registrar cuota/ámbito/ventana y reducir duplicación no requerida; pedir cambio de plan/alcance solo al propietario. Sin pago automático ni recorte crítico. |
| Scanner comercial o GitHub feature no disponible | Elegir abierto/gratuito o revisión manual reproducible autorizada equivalente; declarar límite y mantener gate bloqueado si no cubre el riesgo. |
| Vulnerability feed caído/desactualizado | Registrar versión/fecha/base y estado indisponible; no «cero vulnerabilidades». Revalidar antes de cerrar crítico/release. |
| Test flaky o timeout | Conservar fallo, diagnosticar carrera/infra; retry con historial, no marcar PASS por último intento o excluir sin evaluación de impacto. |
| Secreto en artifact/PR | No publicar evidencia sensible; contener y escalar incidente10.04/09.04; rotación solo bajo autorización operativa correspondiente, sin revelar valor. |
| Preview inaccesible por protección | Ajustar integración autorizada o bloquear; no eliminar auth/protección ni pasar bypass al cliente. |
| Merge check roto/ausente | No fusionar/release; fallo tras main bloquea releases y genera hallazgo, sin bypass por urgencia. |

Resultados que la plataforma llama skipped/unavailable/neutral no significan prueba observada. El agregador requerido exige lista completa y PASS evidenciado de cada control aplicable; la ausencia de check no es verde. NO_APLICA solo con motivo verificable y revisión de impacto, nunca enmascara crítico no validado.

## 15. Observabilidad, retención y recuperación

Registrar runId/job/check/HEAD exacto, módulos/casos/exitcodes, duración/cola, versiones/DB/schema, fallos/cancelaciones/retries y hash/URI de artefacto con QA-Evidence/1. Los links deben permitir al revisor leer el resultado; si caduca evidencia necesaria, reconstituir desde origen confiable o reejecutar bajo permiso, no mantener claim de cierre sin soporte.

Retención de artefactos/backups/logs requiere política07.03/10.03 y presupuesto10.02; no se fija plazo jurídico ni se promete almacenamiento gratuito ilimitado. Fallo corrige origen y produce nuevo runId; no reescribe historial. Release10.04 consume conjunto de checks y manifiestos, sin convertir sumario de agente en aceptación.
