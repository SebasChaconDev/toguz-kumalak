## 2. Objetivo, alcance y valor

Verificar que los modos comprometidos sean utilizables en HTML/3D, ES/EN, teclado/tacto y condiciones de fallos, conservando autoridad Go e intenciones. Incluye componentes, recorridos de dos participantes, móvil, accesibilidad manual y regresión visual reproducible. Vitest/React Testing Library comprueban comportamiento observable; Playwright comprueba navegador y fronteras reales. No se ejecutan estas pruebas ni se crean baselines/assets en lote5.

Una imagen correcta no demuestra legalidad, permiso o accesibilidad. Un test con servidor simulado no se presenta como E2E de persistencia. Local significa dos personas en un dispositivo con transiciones Go disponibles, sin promesa offline.

## 5. Invariantes y entidades

- DOM, canvas, cámara y animación consumen la misma proyección confirmada y controlador. Ningún renderer calcula reglas o confirma resultado.
- Context loss o cambio a HTML conserva commandId/carga/journal de intención pending/unknown; montar un renderer no envía Move/Start/Resume nuevo.
- Animaciones se deduplican por eventos/versiones; huecos requieren reconciliación. Saltar/duplicar/reordenar animaciones no altera estado/Elo.
- HTML permite las funciones esenciales de cada modo: acciones, resultado/causa, ayudas permitidas, cursores y recuperación; undo solo práctica.
- Hint recibido no selecciona una intención activa, no emite move ni cambia timeline/progreso. Ayuda no se ofrece en UI ranked y servidor rechaza sobre recurso oficial identificado.
- Accesibilidad exige pruebas automáticas y uso manual real; axe aislado no acredita WCAG ni lector.

Entidades PROPUESTA: UIObservation/1, BrowserMatrix/1, VisualBaseline/1, AccessibilityReview/1 y ScenarioRun/1, enlazados a QA-Evidence/1. No son contratos de datos deportivos.

## 7. Diseño por capas y matriz de entornos

Componentes prueban estados idle/selected/preview/pending/unknown/confirmed/error/terminal y adapters de eventos/renderer con dependencias controladas. Se observa la petición/salida, foco y texto accesible; no se reimplementa Apply en el test TypeScript. Contratos Go producen los fixtures de referencia revisados, con los errores del servidor como entradas negativas.

E2E real integra web→Identity/Game→PostgreSQL; AI puede ser real local o doble declarado según caso. Los tests de integración no dependen de proveedores reales salvo campaña separada; distinguir fallo de red simulado, respuesta descartada por harness y corte físico observado. Cada caso tiene recursos/usuarios/partidas propios y limpieza por namespace. Probar servidor desde UI y corroborar estado/receipt por lectura autorizada o evidencia SQL de integración.

| Eje | Matriz mínima futura y propósito |
|---|---|
| Motores | Chromium/Firefox/WebKit con releases fijadas; cada crítico se ejecuta en los tres. Diferencias se registran, no se silencian con skip. |
| Participantes | Dos browser contexts reales aislados A/B y, para multitab, dos páginas del mismo contexto A; tercero C para negativos. |
| Presentación | HTML desde carga sin WebGL;3D disponible; pérdida de contexto durante selected/pending/unknown/animating/AI; low/high/reduced motion. |
| Idioma | ES y EN completos, sin claves sin traducir; cambio de idioma no repite comandos ni pierde contexto/foco. |
| Pantalla | Viewports exactos desktop y móvil, orientación vertical/horizontal, zoom/reflow y texto ampliado; propuestas de dispositivos04.04 se fijan antes de campaña. |
| Hardware | Emulación Playwright cubre layout/entradas; Android/iPhone físico y GPU de escritorio comprueban tacto/lector/render/rendimiento real. No equivaler WebKit automatizado a Safari físico. |

En fases incrementales ejecutar todos los modos implementados autorizados y marcar otros NOT_RUN; aceptación de lanzamiento exige matriz comprometida completa. Clasificatorias/Elo dependen de PH06; un stub o una sala casual PH04 no acredita ranked terminado.

3. Integrar Go/servicios/PG de prueba y Playwright con usuarios reales sintéticos en contextos A/B; comprobar estado y red, no solo texto «éxito».
4. Ejecutar modos/acciones y negativos de§13 en los tres motores/ES/EN; separar mocks de integración real y activar fallos controlados.
5. Añadir3D/cámara/animación y transferencia HTML en estados difíciles. Congelar escenas sin animación en curso para comparación; probar orden de animación aparte.
6. Realizar revisión manual de teclado/lectores y dispositivos físicos, con tareas y hallazgos. Automatizar apoyo axe cuando se adopte, sin sustituir inspección humana.
7. Capturar baseline/diff revisados y medidas04.04/09.04. Investigar diferencias de GPU/fuente/foco antes de actualizar referencia.
8. Adjuntar evidencia, clasificar fallos y revisar independientemente. Suite o dispositivo indisponible implica BLOCKED/NOT_RUN del caso, nunca accesibilidad/FPS certificados.

## 10. Justificación y alternativas

Comprobar interfaces observables hace que el test sobreviva refactors y se relacione con uso real. Dos cookies distintas en variables de un mismo contexto no equivalen a dos participantes aislados; contexts independientes permiten carreras/sesiones sin contaminación. HTML primero y mismo controlador permiten probar continuidad durante pérdida GPU, sin otra autoridad.

Visual perceptual detecta degradación de composición; comparación exacta de dominio detecta un contador errado aunque la imagen «se parezca». Lectores y teclado revelan problemas de orden/anuncios que axe no observa. Matriz finita no acredita todos los dispositivos; se documentan cobertura y límites, sin claim universal.

## 11. Ejemplo explicado

Traza sintética prevista para F-Q2-07; no sesión ni captura observada:

```text
A en3D confirma Move(commandId=X,baseRevision="36"); respuesta queda unknown.
Inyectar context_loss -> HTML conserva X/carga/journal y enfoca estado pendiente.
B recibe revision"37"; aviso36 duplicado no retrocede ni dispara animación.
A reconsulta receiptX+Game por scheduler06.02 -> muestra37 y confirma X.
A no envía un segundo Move/Resume por montar HTML; contador Move aceptados=1.
```

Se exige evidencia de red/receipt y foco/DOM antes/después. Si el receipt sigue desconocido, UI conserva unknown; disponer de HTML no demuestra commit.

## 12. Fallos, límites, seguridad y recuperación

Logout/expiración/permiso revocado durante intención conservan error seguro y dejan de ofrecer acciones; un alias/link o invitación no permite leer estado privado. Pantallas de error no imprimen JWT/invitaciones/cookies. Capturas/Playwright traces pueden contener secretos: sanitizar antes de publicar, limitar acceso al original necesario y no usar credenciales reales.

Scheduler06.02/actividad06.03 se conservan: single-flight/caps compartidos30lecturas/min y120/10min de las propuestas consumidoras, sin nuevo polling por canvas/panel. GET/Ably/rival/duplicado no renuevan actividad propia; outage no pausa automáticamente24h y browser no adjudica inconclusa.

Hint/branch/recovery/metadata pedagógica de L4-P01 no son API aprobada por lote5. Casos afectados se mantienen condicionados hasta revisión de05.02/05.03/07.02. UI ranked y recurso oficial conocido rechazan ayudas; un escenario synthetic sin procedencia no permite exigir detección de copia ni bloqueo global de práctica concurrente.

## 15. Observabilidad, corrección y recuperación

UIObservation enlaza requestId/commandId/revisión/eventId con resultados del servidor sin secretos. Medir número de peticiones al cambiar renderer y simultaneidad/caps del reconciliador; no generar actividad por observar. Las trazas de fallos y capturas conservan fuente de baseline/commit, diferencias y decisión humana.

Corregir componente y repetir casos afectados en matriz; conservar evidencia del fallo. Flakiness exige investigar carrera/fuente/temporización y registrar owner, no retry infinito/skip como PASS. Retirar3D temporalmente puede conservar HTML compatible, pero cualquier degradación/release real sigue09.04/10.04 y autorización; no cambia datos o plazo de recuperación.
