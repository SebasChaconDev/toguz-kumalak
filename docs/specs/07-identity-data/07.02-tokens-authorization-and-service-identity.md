## 2. Objetivo, alcance y valor

Precisar qué prueba acepta cada receptor, cómo valida firma/emisor/audiencia/tiempo, quién puede actuar sobre cada recurso y cómo fallar de forma segura cuando falta Identity o material de confianza. Separar Google, acceso del producto, identidad de servicios y capacidades Ably impide convertir una credencial de un ámbito en permisos de otro.

Comprende acceso asimétrico/JWKS, cookies del mismo origen por rewrites, CSRF, roles/recurso, S2S, secretos/rotación y controles de abuso compatibles con Functions concurrentes. Consume el ciclo consolidado de [07.01](07.01-oidc-guests-and-session-lifecycle.md): invitados renovables, margen recuperable, prepare/commit/recibo de refresh, vínculo y límite de revocación. No modifica elegibilidad ni crea un cuarto servicio, Redis obligatorio o una consulta Identity por movimiento.

Los contratos de esta spec son lógicos y versionados para que [05.02](../../index.md#spec-05-02), `EN_REVISIÓN`, fije transporte/OpenAPI y errores; las tablas/locks serán de [05.03](../../index.md#spec-05-03), `EN_REVISIÓN`. La misión autorizada en [AGENTS](../../../AGENTS.md)/[PLANS](../../../PLANS.md#lote-3) es documental: no configurar proveedores, emitir claves/tokens, implementar, instalar, ejecutar pruebas de producto o desplegar. Un requisito escrito no demuestra su eficacia.

## 5. Invariantes y entidades de confianza

| Frontera | Emisor → receptor / propósito | Regla de exclusión |
|---|---|---|
| Google | Google → Identity, acreditar identidad externa durante login/link | ID/access/refresh Google no son acceso Game, S2S ni Ably |
| Producto | Identity → Identity/Game, principal UUID guest/user/admin de sesión propia | Firma válida no reemplaza autorización por recurso; AI no acepta token de navegador |
| S2S | Servicio identificado → receptor concreto por operación permitida | No representa automáticamente al usuario ni se transforma en participante/administrador |
| Ably | Game mediante credencial Ably → Ably, capacidad temporal del canal exacto | No acepta comandos oficiales; navegador no publica ni usa ese token como acceso REST |

- Los validadores se seleccionan por endpoint/operación esperados y configuración confiable, nunca por una URL/clave/rol aportados por el token.
- `sub` del acceso es UUID del producto; `sub` S2S pertenece a namespace de servicio y otro tipo/emisor. Google `sub`, alias y UUID no se intercambian.
- Game valida firma/emisor/audiencia/tiempo y recurso localmente; no consulta Identity por jugada ni acepta firma ausente para mantener disponibilidad.
- Usuario/servicio/Ably tienen claves y permisos separados por entorno. Material público JWKS nunca contiene privada, secreto de cookie/recibo ni API key Ably.
- JWT es portador de datos firmados, no cifrados: no incluir correo, tokens Google/refresh, URLs privadas, listado de cuentas vinculadas o PII innecesaria.
- Alias/URL/código de sala solo localizan una intención; recuperar/mover requiere principal original autorizado. Admin y vínculo de historial tampoco eligen un participante por body.
- Revocar refresh no borra la validez criptográfica de un acceso ya emitido ni de una capacidad Ably vigente. Se documenta su límite temporal, sin revocación global instantánea supuesta.
- Contador por Function en RAM no representa límite global. Propiedad SQL sigue en Identity/Game y AI permanece sin DB propia.

Entidades propuestas: `UserAccessClaims`, `ServiceClaims`, `VerifiedPrincipal`, `TrustedKeySet`, `CSRFBinding`, `RateBucket`, `AIComputeGrant`, `AIClaimReceipt` y `AblyCapabilityGrant`. No son structs compartidos de persistencia ni código creado en este lote.

## 7. Diseño técnico y responsabilidades

### Acceso propio: forma y validación

Perfil lógico `user-access/1`, **PROPUESTA**: JWS compacto, algoritmo permitido únicamente `ES256` con curva P-256, clave exclusiva de firma de acceso Identity. `typ=tk-user-at+jwt`, `kid` único por clave/entorno, de 1–64 caracteres ASCII `[A-Za-z0-9_-]`. No aceptar `none`, HMAC, otro algoritmo, `jwk` embebido, `jku`, `x5u`, `x5c`, `cty`, compresión, JSON duplicado o headers críticos no implementados. La allowlist pertenece al receptor y vincula algoritmo/tipo/uso a cada clave; no se amplía leyendo `alg` no confiable.

| Claim obligatorio | Semántica propuesta / validación |
|---|---|
| `ver` | Entero `1`; perfil conocido, sin defaults ante versión desconocida |
| `iss` | Emisor Identity del entorno, URI exacta configurada; sin derivar de Host/headers cliente |
| `aud` | Conjunto exacto `['tk-identity','tk-game']` para esta sesión web; cada receptor exige su audiencia. Sin `tk-ai` ni audiencia S2S |
| `sub` | UUID inmutable de sujeto Identity, nunca alias/correo/ID Google |
| `sid` | ID opaco de familia; correlación y CSRF, no permiso de consultar sesiones ajenas |
| `jti` | ID aleatorio único de emisión; no garantiza uso único del acceso por sí solo |
| `iat`, `nbf`, `exp` | NumericDate enteros; `nbf=iat`, `exp=iat+900 s`, `0 < exp-iat <= 900 s`; 900 s es concreción propuesta de ~15 min |
| `identity_kind` | `guest` o `registered`; coherente con rol y origen de alta |
| `roles` | Lista única acotada de guest/user/admin; guest no contiene user/admin; registered contiene user y admin solo por concesión server-side |
| `profile_ready` | Booleano; alias/onboarding completos para nuevas ranked. No cambia elegibilidad de una partida existente |
| `session_recoverable_until` | NumericDate de `sessionRecoverableUntil` de 07.01; no se inventa desde el cliente; `exp+30 s+24 h <= valor` al conceder acceso apto para nueva ventana Game |
| `csrf_hash` | Base64url SHA-256 del nonce CSRF aleatorio de la familia; liga cabecera/cookie a este principal sin consulta Identity |

No hay `linkedSubjects`, actor alternativo, color, Elo ni permiso global de partida en el JWT. UUID es el único principal humano de esa petición. Cambios de alias/vínculo no renumeran `sub` ni las claves idempotentes. Un acceso emitido antes de promoción puede conservar clase guest hasta vencer; Game no recalcula elegibilidad por ello. Emisión de registrado cerca del absoluto de 07.01 requiere reautenticar si no cabe el margen de recuperación; no emite una reserva falsa.

Pipeline propuesto de receptor:

1. Fijar política esperada por operación: navegador/producto o S2S, emisor/audiencia/tipo y credencial permitida. Rechazar fuentes duplicadas/ambiguas, tamaños excesivos o JSON/encoding inválidos antes de trabajo costoso.
2. Parsear header acotado solo para localizar `kid` dentro del conjunto confiable de esa política. Ninguna URL/issuer recibido cambia origen de claves. Resolver caché conforme al siguiente apartado.
3. Verificar firma y compatibilidad exacta de algoritmo/clave; después confiar en claims. Validar tipos, `ver`, issuer exacto, audiencia y coherencia de clase/roles; no usar claims sin firma para SQL o autoridad.
4. Usar reloj confiable del servidor; tolerancia propuesta de 30 s: admitir solo `now < exp+30 s`, `now+30 s >= nbf` e `iat <= now+30 s`. Caducidad del token en el borde de igualdad se rechaza. Edad máxima y `exp-iat` impiden tokens de larga vida fabricados por error. El tiempo DB determina las mutaciones y el deadline Game, según 07.01.
5. Aplicar origen/CSRF si es navegador, cuota/validación, permiso de recurso y fase/revisión. Para conceder ventana Game comprobar `tGameDB+24 h <= session_recoverable_until`; no basta firma. Mutación no autorizada no ejecuta motor ni modifica resultado.

Solo se acepta credencial navegador en cookie de acceso. Los endpoints internos S2S usan Authorization Bearer de servicio y no aceptan cookies como fallback. Clientes nativos/bearer de usuario no forman parte de este contrato MVP. El API devuelve principal interno verificado con `subjectId`, `familyId`, clase, roles, readiness, expiración y horizonte; los handlers no construyen ese principal desde un body.

Matriz de recurso/acción propuesta que conserva los modos y reglamento aprobados; el permiso de turno se aplica únicamente donde la acción lo exige:

| Recurso / acción | Permiso de principal y estado |
|---|---|
| Online, mover | guest/user participante original del color con turno, partida activa, revisión vigente; admin solo si además es ese participante |
| Online, reclamar repetición | Cualquiera de los dos participantes, tenga o no turno, posición activa en ventana R-07 y umbral/revisión verificados atómicamente; nunca tercero o espectador |
| Online, renunciar/ofrecer tablas/aceptar tablas | Participante original y fase/revisión válidas; renuncia no exige turno, aceptar requiere oferta del otro y consentimiento bilateral, no oferta propia |
| Online, leer estado privado/emitir capacidad Ably | Participante original autorizado y estado/plazo compatible; sin permiso implícito por alias, invitación, admin o vínculo de historial |
| Local dos personas en un dispositivo | Una sesión propietaria del recurso local puede controlar ambos bandos según el flujo aprobado; no exigir dos UUID online. Simulación Go valida estado/origen/turno interno sin resultado competitivo |
| Práctica/escenario | Sesión propietaria de la rama, controles de ambos bandos/undo según modo, entradas/versión válidas por Go; puede enviar tablero de escenario únicamente a simulación sin autoridad oficial, Elo ni historia confiable online |
| Historial terminado | Propio o concesión concreta confirmada de lectura; replay no autoriza continuar/mover. Asociación G→U conserva UUID/recibos originales |

Game deriva actor/modo/recurso autorizado; un modo enviado por cliente se contrasta con el recurso persistido o contrato de simulación. No acepta un escenario/estado cliente para sustituir una partida oficial. Admin no adjudica ganadores ni mueve en partida ajena por su rol. Los casos ACC-N1 de repetición y precedencia mantienen sus esperados; no se añaden espectadores, relojes o requisitos de dos identidades a local/práctica.

### JWKS público, caché y rotación

Identity publica `UserJWKS/1` mediante operación pública de lectura que 05.02 ubicará; URL HTTPS absoluta configurada por entorno, distinta de Google Discovery y de claves S2S. JWK propuesto: `kty=EC`, `crv=P-256`, `alg=ES256`, `use=sig`, `kid`, `x`, `y`; si aparece `key_ops`, solo `verify` compatible. No publicar `d` ni otra privada. Rechazar claves duplicadas para un kid, parámetros inválidos, curva/tipo/uso incompatibles y conjuntos excesivos.

| Parámetro propuesto | Regla concreta |
|---|---|
| Tamaño y cantidad | Hasta 64 KiB y 8 claves públicas por conjunto; JWT propio hasta 3.072 bytes para caber en cookie con sus atributos y claims/roles acotados; valores se validarán con cookies reales |
| Fetch | Timeout 2 s, HTTPS verificado, sin redirects ni URL recibida del token; validar respuesta completa antes de sustituir snapshot |
| Frescura | Máximo local 300 s desde validación exitosa, acotado además por Cache-Control/Age del origen; sin stale-while-revalidate/stale-if-error para aceptar autenticación |
| Renovación | Single-flight por instancia/conjunto; revalidación condicional con ETag si procede. Un 304 solo refresca snapshot ya validado bajo política/edad HTTP correcta |
| kid desconocido | Un fetch forzado acotado si no hay fetch reciente; máximo uno por conjunto/instancia cada 30 s, con caché negativa 60 s de hasta 64 kids; después rechazo, sin buscar fuera del emisor fijo |
| Rotación ordinaria | Prepublicar K2 al menos 600 s antes de firmar con ella; detener emisión K1 y mantener pública K1 durante 1.800 s desde su última emisión; separar retirar privada de retirar pública |

Los límites son política de aplicación, no valores impuestos por RFC. La edad efectiva incluye `Age` y tiempo transcurrido; no reiniciar 300 s descargando una copia vieja desde un intermediario. Un fetch inválido/fallido no cambia ni rejuvenece el último snapshot. Un conjunto que no contiene el kid no permite probar firma con cualquier otra clave ni omitir verificación.

| Estado de material/token | Decisión segura |
|---|---|
| kid conocido, snapshot aún fresco, token válido | Validar localmente; Identity puede estar caído. Sin llamada de sesión/perfil por movimiento |
| kid desconocido, fetch exitoso y clave compatible encontrada | Verificar firma y resto de claims; no aceptar solo por encontrar un kid |
| kid desconocido tras fetch válido | Rechazar `TOKEN_KEY_UNKNOWN`; no validar con fallback genérico |
| No hay snapshot, está vencido o fetch obligatorio falla | `AUTH_VALIDATION_UNAVAILABLE`; no ejecutar operación. No aceptar clave vencida indefinidamente |
| Firma/audiencia/emisor/tiempo inválidos | Rechazar `TOKEN_INVALID`/`TOKEN_EXPIRED` según error seguro; no confundir con dependencia no disponible |

Una instancia fría durante caída Identity puede no validar aunque otra tenga caché fresca. Memoria local es optimización de verificación, no almacén autoritativo de sesión; su pérdida reduce disponibilidad y nunca autoriza bypass. Unknown-kid floods no deben provocar fetch ilimitado distribuido: además del límite local, el endpoint JWKS y admisión pública tienen límites propios; las cuotas reales/edge requieren factibilidad futura, sin afirmar protección DDoS demostrada.

La prepublicación/solapamiento exceden cache y vida corta propuestas; antes de retirar K1 se demuestra que ningún despliegue sigue firmando con ella. Claves comprometidas pueden requerir retirada urgente y expulsión de cachés mediante configuración/despliegue; hasta que el receptor observe revocación o venza el snapshot/token existe una ventana residual. No prometer revocación instantánea ni mantener una clave comprometida únicamente para cumplir solapamiento ordinario.

### Navegador del mismo origen, cookies y CSRF

`LogoutAll/1`, propuesta de política de recurso Identity: sesión registrada y familia vigentes comprobadas en su propia DB, confirmación explícita de intención y Origin/CSRF válidos. Revoca únicamente familias del sujeto autenticado, nunca un subjectId del cliente. No exige un mecanismo adicional de reautenticación no definido; el límite residual de JWT emitidos permanece. Esta comprobación local de Identity no introduce introspección por movimiento en Game.

Web y APIs Identity/Game se exponen bajo un origen externo HTTPS permitido por entorno mediante rewrites; AI solo por HTTPS interno protegido. El origen externo esperado y destinos upstream son configuración, nunca Host/X-Forwarded-* arbitrarios. CORS de navegador no permite otros orígenes con credenciales; tampoco se considera una autorización S2S. Acceso directo a upstream conserva verificación completa y no confía en estar oculto detrás del rewrite.

Tabla de cookies **PROPUESTA**. `identityPrefix` es el namespace externo reservado a Identity, propuesto `/api/v1/identity`; 05.02 debe consolidarlo para que callback/refresh queden dentro de él. No se fijan aquí rutas de operaciones independientes. Ninguna cookie establece `Domain`; todas son host-only y `Secure`. Los prefijos y Path se prueban en navegadores reales.

| Cookie | Atributos/vida y finalidad |
|---|---|
| `__Host-tk-access` | HttpOnly, Secure, SameSite=Lax, Path=/; Max-Age 900 s. JWS propio; no se devuelve token en body/JS |
| `__Secure-tk-refresh` | HttpOnly, Secure, SameSite=Lax, Path=identityPrefix; cookie persistente instalada al emitir cada credencial hasta su deadline lógico +48 h. Guest: lógico48h/cookie96h máximas desde emisión; registrado: min(idle7d, absoluto30d)+48h de transporte, sin extender ese absoluto lógico |
| `__Secure-tk-refresh-attempt` | HttpOnly, Secure, SameSite=Lax, Path=identityPrefix; cookie persistente hasta preparedAt+48 h, acotada además por recibo cuando exista, sin reiniciar por commit/retry; derecho a comprometer preparación nueva solo 5 min y replay solo dentro del recibo confirmado vigente |
| `__Secure-tk-oidc-context` | HttpOnly, Secure, SameSite=Lax, Path=identityPrefix; 10 min, correlación de navegador/transacción; no credencial de juego |
| `__Host-tk-csrf` | Secure, SameSite=Lax, Path=/, legible por JS y PERSISTENTE hasta el mismo deadline lógico de la credencial emitida +48 h que refresh; nonce aleatorio256bits estable por familia y hash conservado. No autentica; se copia a cabecera y no a localStorage. Commit perdido conserva cookie/nonce padre aun al cerrar/reabrir navegador |
| `__Secure-tk-dataop-<operationId>` | PROPUESTA07.03: HttpOnly/Secure/Strict/host-only, Path=/api/v1/identity/data-operations; ticket256bits de una raíz delete, persistente hasta preparedAt+30d. Prepare autenticado instala antes de revocar; no credencial de usuario/export/Game |
| `__Host-tk-dataop-csrf-<operationId>` | PROPUESTA07.03: Secure/Strict/Path=/, legible por JS, sin Domain; nonce op-específico hasta preparedAt+30d, copiado a X-TK-Data-CSRF. No lo elimina logout/revocación de familia por wildcard |

Path de refresh/intento/contexto evita enviarlos a rutas Game/AI del navegador; middleware rechaza duplicados del mismo nombre y no usa cookies con Domain/Path ambiguos para escoger principal. Path reduce exposición, pero no es frontera contra código malicioso del mismo origen. El prefijo `__Secure-` no impide por sí solo inyección desde subdominio: host-only, ausencia de CORS confiado a subdominios, nombres únicos y rechazo de duplicados son obligatorios en esta propuesta. `__Host-` exige Path=/ y ausencia de Domain; no se usa para refresh de path restringido.

El nonce CSRF permanece estable dentro de la familia durante refresh para no invalidar peticiones legítimas de otras pestañas. Identity guarda su hash en familia y lo firma como `csrf_hash` en cada acceso. En mutación de navegador, además de cookie acceso/refresco adecuada, el cliente manda `X-TK-CSRF` con el nonce; receptor exige igualdad header/cookie y SHA-256 igual al binding firmado o al hash de la familia para refresh con acceso expirado. El padding persistente de CSRF/refresh se instala ya al emitir el padre; por eso no depende de recibir la respuesta commit. Para recuperar recibo con padre consumido/expirado se exige además padre exacto/proof/fingerprint, familia y sucesor activos/no revocados y recibo vigente; el nonce no se regala mediante GET ni basta una proof aislada. Comparaciones seguras y validación de origen son adicionales. No se transmite nonce por URL, logs o BroadcastChannel. No es un secreto bearer que pueda autenticar sin la cookie HttpOnly.

Origen propuesto: para toda mutación de navegador exigir `Origin` exacto (scheme/host/port) del entorno; `null`, ausente, subdominio o sufijo parecido se rechazan. No fallback permisivo a Referer o headers reenviados sin verificar. Se requiere JSON y cabecera personalizada para operaciones API mutantes; formularios cross-site y GET mutantes no se admiten. La creación inicial guest/BeginOIDC sin familia utiliza origen exacto, content-type y cabecera de intención personalizada como defensa de pre-sesión; el servidor no acepta CORS cross-origin y no muta mediante GET de bootstrap. Después de crear familia se exige también binding CSRF. Esta elección excluye clientes que no produzcan dichos encabezados y debe comprobarse en el cliente real.

El callback Google GET es excepción **solo** a la regla de Origin/CSRF de API: la navegación cross-site puede no contener Origin. Requiere cookie de contexto Lax, state de uso único, transacción/correlación vigente, intención, nonce del ID token, PKCE y redirect exacto conforme a 07.01. No acepta un callback como operación genérica ni modifica otro recurso; respuestas de callback eliminan code/state de la URL mediante redirección a retorno local permitido, sin contenidos terceros ni secretos en logs. Uso de form_post requeriría revisar SameSite y no está elegido aquí. SameSite=Lax permite callback GET superior; no sustituye controles CSRF ni evita XSS.

Respuestas con credenciales, contexto/estado privado o Set-Cookie usan `Cache-Control: no-store`; no caches compartidas por usuario ni URLs con tokens. Un frontend no lee refresh/acceso y no convierte Google/Ably en cookies de acceso propio. Logout borra cookies con exactamente Path/nombre/atributos de emisión; un conflicto `REFRESH_ADVANCED` no las borra indiscriminadamente.

### Seguimiento limitado de una eliminación ya confirmada

El seguimiento delete de [07.03](07.03-profiles-history-and-data-rights.md) es una frontera op-específica adicional, sin convertirlo en login: prepare exige U vigente/CSRF familiar/origen y guarda receipt cifrado para reproducir las mismas cookies si se pierde respuesta. Confirm inicial exige todavía U del titular, ticket/nonce/origen y plazo10min desde prepare. Después de confirm durable/revocación solo retry exacto de esa fase/raíz/hash y lectura segura admiten el ticket/nonce sin JWT; nunca otro UUID, export o nueva confirmación prepared. Hashes/receipt cifrado tienen separación de propósito/AAD raíz/sujeto/familia/fase/expiración, claves separadas según custodia. Vida30d no extiende los10min iniciales y no se renueva por retry. GET de estado valida ticket, cookie/cabecera nonce, Origin exacto si presente y Sec-Fetch-Site no cross-site si presente; no exige Origin/Referer ausentes legítimamente, no muta/coordina ni entrega secretos y CORS sigue cerrado. POST exige Origin siempre. Máximo dos raíces por contexto y dos preparaciones nuevas/día/sujeto son propuestas07.03; cookies con nombres por UUID no se sobreescriben entre raíces. Logout borra exclusivamente nombres/rutas de sesión y conserva esas pruebas limitadas hasta su expiración/revocación propia. Perder todas las pruebas limita UI; no hay recuperación OIDC de cuenta blocked inventada.

### Link Google sin reemplazar la sesión invitada

Diseño concreto **PROPUESTA** para vínculo G→U existente: `BeginOIDC(intent=link)` está ligado a la familia G, y el callback solo acredita U dentro de un registro privado `LinkProof` de uso único, caducidad 10 min y alcance `completed_history_read`. **No inicia sesión de producto U ni reemplaza las cookies G**. La UI muestra confirmación del vínculo y conserva G para sus activas; la prueba externa U no se convierte en bearer de usuario en el navegador.

`ConfirmIdentityLink` exige prueba vigente G, binding CSRF/origen y LinkProof U de la misma intención/familia/operación. Identity consume ambas autorizaciones para la relación de 07.01 y coordina historial terminado; no entrega `linkedSubjects` ni escoge actor por parámetro. Si U ya es rival de G en activa, la activa sigue excluida y JWT G/U mantienen participantes originales. Cancelar o vencer LinkProof no cierra G ni cambia su historial. La promoción cuando Google aún no tenía cuenta conserva UUID G; puede emitir una nueva familia registrada y revocar la anterior, manteniendo participante UUID y condición deportiva inicial.

Un login posterior a U es una intención separada explícita: antes de cambiar el único contexto de cookies, advertir que G controla sus activas y que sustituir las credenciales de ese contexto puede impedir retomarlas. La opción propuesta es terminar las activas como G y luego iniciar sesión U, o usar otro perfil de navegador para U; no se exportan cookies ni se conserva un selector de actor controlado por body. No cambiar sesión por el callback de link. El usuario puede cancelar el cambio y seguir como G; esto no impide asociar historial ya terminado. Si decide login explícito, nueva sesión U no hereda permisos G y las consecuencias de perder la prueba G permanecen visibles conforme a 07.01.

### Refresh, recibos y criptografía de custodia

Se conserva prepare/commit/recibo de 07.01; no se emite JWT de 48 h. Refresh/proof/nonce son opacos aleatorios de 256 bits; hashes servidor SHA-256 con separación de propósito/versionado. La gran entropía permite hash para opacos, no avala hashing rápido de passwords; no hay contraseñas propias.

`RefreshAttempt` y `RotationReceipt` usan cifrado autenticado propuesto AES-256-GCM, nonce aleatorio único por cifrado con clave, versión/keyId y AAD de familia/generación/attemptHash/fingerprint/expiración. Clave diferente de firma acceso, S2S, CSRF y Ably; validar autenticidad/AAD antes de reproducir. No derivar claves privadas desde UUID ni reutilizar nonce. Biblioteca y manejo seguro de claves/aleatoriedad quedan POR_VERIFICAR, sin implementar primitivas propias.

La respuesta de preparación instala cookie de intento hasta `preparedAt+48 h`; commit/retry conservan ese límite absoluto o uno menor si lo impone el recibo, sin reiniciar su vida. Refresh y CSRF ya se emitieron con retención hasta `credentialLogicalDeadline+48 h`; este padding previo conserva el padre aun si la respuesta commit nunca llegó y su plazo lógico ya venció. El derecho a comprometer una operación nueva sigue siendo solo 5 min: después la prueba sirve únicamente para buscar un recibo confirmado coincidente; si nunca hubo commit, debe preparar intento nuevo con credencial corriente lógicamente vigente. Un padre vencido no consumido nunca rota. Familia/sucesor/recibo deben estar vigentes y no revocados; el absoluto registrado no cambia. Reproducir recibo usa expiraciones de cookies/JWT/horizonte originales, nunca plazos calculados nuevamente desde retry. Retención de transporte y vigencia lógica son distintas; 07.01 conserva esta separación.

Línea temporal propuesta, horas relativas: padre emitido0h con deadline lógico48h y cookies refresh/CSRF hasta96h; prepare+commit47h emiten sucesor lógico95h y recibo como máximo hasta95h, con proof de preparación hasta95h. Respuesta commit perdida; después de cerrar/reabrir navegador, retry71h conserva padre exacto, proof y nonce CSRF originales. Recuperar recibo reproduce resultado47h sin nuevas credenciales ni ampliación de exp/horizonte; el JWT reproducido ya expiró, y una emisión nueva exige después la credencial sucesora corriente vigente. Nonce inventado, proof sola o padre expirado no consumido se rechazan aunque sus cookies aún existan.

Ante padre consumido, buscar recibo coincidente antes del rechazo por expiración original del padre. Exigir familia y sucesor aún vigentes/no revocados y proof/hash/fingerprint/límite correctos. Se restituye exactamente el sucesor/acceso original, sin extender exp/horizonte. Para nueva rotación, en cambio, siempre credencial corriente vigente. Recibo cuyo sucesor ya se consumió no entrega secreto; `REFRESH_ADVANCED` obliga a reconciliar contexto compartido. La purga/cambio de clave puede romper esa recuperación y debe ser observable, sin recuperar por alias.

### Identidad servicio a servicio

Perfil `service-access/1`, **PROPUESTA**: ES256/P-256 con claves distintas de acceso usuario y una privada exclusiva por servicio/entorno. Cada servicio firma sus credenciales de llamada corta; destinatarios configuran issuer, sub y claves públicas del llamador mediante keyring confiable versionado por despliegue. No se requiere consultar Identity para firmar una llamada Game→AI o verificar AI→Game. Un JWKS S2S futuro solo puede reemplazar esa distribución con igual política acotada/aprobada; no se sigue ninguna URL del JWT.

Claims obligatorios: `ver=1`, `typ=tk-service-at+jwt` en header, kid, `iss` de servicio/entorno configurado, `sub=svc:identity|svc:game|svc:ai`, **una** `aud=svc:<receptor>`, `iat/nbf`, `exp<=iat+120 s`, `jti` aleatorio y `scope` de operación permitido. Claims de binding obligatorios: `op` identifica la operación lógica versionada, `http_method` el método HTTP en mayúsculas, `request_id` la correlación de esta intención, `body_sha256` el hash del body validado y `params_sha256=SHA256(JCS({pathParams,queryParams}))` el de parámetros tipados. Objetos vacíos se incluyen explícitamente cuando no hay parámetros; body ausente se representa mediante objeto vacío para ese hash. Receptor mapea `op`+`http_method` a la ruta de 05.02, obtiene parámetros del request recibido, decodifica una sola vez, valida tipos/esquema y calcula ambos hashes; rechaza parámetros repetidos/desconocidos, rutas que no corresponden a la operación o bindings distintos. Cambiar recurso en URI/query no conserva autorización aunque el body sea igual. `request_id` no sustituye commandId/operationId ni idempotencia de negocio. Rutas HTTP concretas se consolidarán en 05.02 sin cambiar esta operación firmada. No contiene roles humanos ni token Google/usuario como sustituto de identidad de servicio.

Codificación propuesta `domain-json/1`: JCS exacto de [RFC 8785 §3.2](https://www.rfc-editor.org/rfc/rfc8785.html#section-3.2), consultado el 2026-10-21, restringido a enteros seguros entre `-(2^53-1)` y `2^53-1`; campos uint64/revisiones se representan como strings decimales tipados, sin ceros iniciales salvo `0`. UTF-8 sin BOM, sin normalización Unicode, claves de esquema ASCII; rechazar duplicados/desconocidos, Unicode inválido y valores no enteros/fuera de rango antes de perder precisión. Orden/escaping de strings son los de JCS, sin escaping HTML adicional de `<`, `>` o `&`; no basta el serializer JSON por defecto de Go. El hash SHA-256 se calcula sobre esa representación del body validado completo, sin el token Authorization que viaja en header. `calculationPayload` es el objeto completo de posición/contexto/base/versiones/dificultad/presupuesto, sin campos de su propio hash; `payloadHash` del grant cubre ese objeto entero. La llamada AI contiene `{grantJti, calculationPayload, payloadHash}` y el `body_sha256` S2S cubre todo ese sobre, evitando referencia circular y payloads no ligados.

| Llamador → receptor | Scopes propuestos y límites |
|---|---|
| Game → Identity | `profiles.public.read.batch`; selector de UUID permitidos o alias registrados públicos exactos (uno solo), devuelve UUID/perfiles mínimos o ausencia. Sin sesiones/refresh/correo/perfiles privados; variantes y normalización posterior al hash en05.02/07.03 |
| Identity → Game | `history.associate`, `history.association.read`; fuente/objetivo/operationId/alcance fijo de 07.01. Para borrado futuro `data.cleanup.request`/`data.cleanup.status`, sujetos/operación verificados por 07.03, sin permiso de mover ni alterar Elo |
| Game → AI | `ai.compute`; posición/contexto/versiones, grant jti/hash y presupuesto autorizados por Game. No permite publicar ni consultar DB |
| AI → Game | `ai.grant.consume`; solo claim de grant por intento AI y consulta idempotente del mismo claim. Sin scopes partida/participante/Elo/perfiles |

Los endpoints internos aceptan únicamente S2S y lista explícita de llamador/audiencia/scope/operación, con HTTPS/certificado/hostname verificados. Un JWT `svc:game` recibido por API de movimiento de usuario se rechaza aunque firme una clave conocida. El destinatario no acepta credencial propia como si fuera la del llamador; no hay credencial universal compartida. CORS cerrado no autentica S2S y estar en Vercel tampoco. TLS/ingress y protección de previews se demostrarán en 01.02/10.01, sin crear un recurso real.

`jti` de un S2S ordinario correlaciona y limita vida; no promete un solo uso sin estado. Operaciones de datos deduplican por operationId/payload y vuelven a autorizar alcance; cálculos usan el protocolo siguiente. El solapamiento propuesto de claves S2S es al menos 600 s después de última emisión vieja, superior a 120 s+30 s; desplegar públicas receptoras antes de activar privada nueva. Revocar privada/issuer requiere actualizar keyrings receptores; credenciales ya emitidas tienen ventana residual hasta exp/actualización observada. No se firma con clave usuario para saltarse ese límite.

### Antiabuso persistido y grant IA

Política inicial **PROPUESTA** con contadores atómicos por ventana UTC en PostgreSQL del dueño: Identity para invitados/OIDC/sesiones; Game para salas/comandos/capacidades/IA. Actualizar todos los buckets aplicables en transacción corta, incrementando solo si todos caben; en exceso rechazar sin operación de negocio y devolver intervalo seguro hasta reinicio. La clave combina entorno, operación, UUID/familia/recurso cuando verificados e IP pseudonimizada para preautenticación; no alias. IP solo desde proxy de confianza configurado; X-Forwarded-For arbitrario no elude límites. Rotación/retención de pseudónimos sigue política 10.02/privacidad; no guardar IP en claro por conveniencia.

Ventanas fijas permiten ráfaga al cruzar su frontera; se prueba ese límite y no se declara token bucket continuo. Los valores se revisarán con carga/quotas sin recortar el lanzamiento base/ampliado. Mensajes/headers/cuerpos se limitan antes de parsear; propuesta inicial cuerpo API hasta 64 KiB para cálculos/operaciones complejas y 8 KiB para autenticación ordinaria; 05.02 concretará por recurso. Límites de alias/versiones/campos se validan server-side por su dueño. Si no se puede comprobar/reservar cuota persistida, operación costosa/mutante falla cerrada `RATE_LIMIT_UNAVAILABLE`; no cambiar a contador RAM que reinicie por instancia.

AI es stateless sin DB. Game controla toda solicitud pública de cálculo y persiste `AIComputeGrant` antes de llamar AI: jti único, sujeto/recurso autorizado, revisión base/versiones, hash canónico del **payload completo**, presupuesto, issuedAt/deadline y estado `issued`. Presupuesto contiene `maxElapsedMs`, `maxNodes`, `maxDepth`, límite de payload y cancelación; son números positivos seleccionados por política de Game, no libre elección del cliente. En esta versión de seguridad se propone un sobre máximo inicial de 1.000 ms, 200.000 nodos y profundidad 32; son techos de admisión POR_VERIFICAR, no fuerza ni objetivos de búsqueda. 08.01/08.02 deberán demostrar/adaptar presupuestos de fácil/normal mediante propuesta sin sobrepasar cuotas o cambiar estas condiciones silenciosamente.

Protocolo lógico `ClaimAIGrant/1`, propuesta canónica de autorización/antiabuso aquí; 05.02 define transporte y 05.03 persistencia, sin convertirlos en dependencias inversas:

1. Game autoriza usuario/recurso/revisión, reserva cuota y persiste grant con deadline máximo 120 s y mismo hash/budgets que la llamada; confirma **antes** de HTTP. No mantener transacción o lock de partida durante AI/callback.
2. AI valida localmente S2S de Game, scope, audiencia, tiempo, operación, hash y techos. Genera `attemptId` aleatorio internamente para este handler; nunca usa uno elegido o devuelto por el cliente/Game para retomar otro cálculo.
3. AI llama `ConsumeAIGrant` de Game mediante su propia credencial `svc:ai`/aud `svc:game`/scope `ai.grant.consume`, con jti/hash/budgets/attemptId. Game comprueba la reserva, tiempo DB y límites exactos; CAS `issued→claimed` asigna ese intento y persiste recibo. Otro attemptId obtiene `AI_GRANT_ALREADY_CLAIMED`, sin autorización para calcular.
4. Si se pierde respuesta del callback, el **mismo handler AI** repite misma intención/attemptId/hash mientras grant siga vigente. El recibo puede confirmar el mismo claim; no crea un permiso nuevo ni ordena otro cálculo. AI no comienza hasta conocer autorización vigente. En este handler un estado interno `not_started→running→finished` impide iniciar de nuevo por callback duplicado.
5. Nueva petición/replay al endpoint AI crea otro handler y otro attemptId: no puede reutilizar claim anterior. Reinicio/crash tras claim consume grant y puede no producir resultado; no se recupera attemptId desde el cliente, caché compartida o JWT para ejecutar de nuevo. No hay exactamente una vez de cómputo ni entrega garantizada.
6. Timeout incierto de callback no autoriza cómputo. Propuesta: hasta dos reintentos acotados con backoff dentro de deadline; si no se resuelve, cancelar. Reintentar cálculo requiere nueva autorización/cuota y nuevo grant de Game, acotado por el mismo límite público, o respaldo de la fuente 08.02 cuando se concrete. Nunca reenviar automáticamente en bucle el mismo grant para «forzar» resultado.
7. AI respeta tiempo/nodos/profundidad, cancela al alcanzar límite y devuelve referencia de grant/base/versiones. Game revalida legalidad/revisión/fase antes de aceptar recomendación; AI no aplica jugada. Game puede marcar `completed` al recibir resultado correlacionado, liberando su cupo de concurrencia sin volver utilizable el grant; crash/silencio retiene reserva hasta deadline. Consumo/completado de grant no es commit de partida ni Elo.

Esto añade dos llamadas de red respecto de cálculo local (Game→AI y AI→Game), almacenamiento/cuota y dependencia Game durante admisión; su latencia/coste se medirán. AI falla cerrada si Game no puede confirmar claim. Un atacante con clave privada del servicio es compromiso mayor: límites por grants y separación de scopes reducen alcance, pero no constituyen prueba de integridad de un servicio comprometido. La RAM de AI solo guarda estado de su handler; el rechazo global de replays depende del CAS persistido Game. No se añade DB AI, Redis, cola o cuarto servicio.

### Capacidad Ably restringida

Solo Game solicita/firma capacidad usando API key Ably privada. Antes de emitir, verifica JWT propio, rol+participante y permiso sobre sala/partida, horizonte/estado y rate limit. Propuesta: canal exacto `env:game:<gameUUID>`, `clientId` fijo al UUID propio y capability únicamente `message-subscribe`; sin comodín, publish, presence, history, object/annotation ni derechos globales. No omitir capability: la omisión puede heredar todos los permisos de la clave. La clave publicadora Game es distinta de la destinada a mint de suscripción y se restringe al namespace pertinente; las posibilidades exactas de configuración/SDK se verifican después.

TTL nominal propuesto 300 s, con expiración estricta `min(tGameDB+300 s, userAccess.exp, session_recoverable_until, resourcePermissionUntil)`. No usar leeway del JWT para extender capacidad. Si exp resultante no es futura, solicitar renovación/reconciliación; no emitir token mínimo que sobrepase el permiso. Para activas, `resourcePermissionUntil` no supera deadline recuperable Game; para salas pendientes no supera su plazo; terminadas no reciben nuevas capacidades de juego y se leen por REST autorizado. Cambios de estado/revocación pueden dejar una capacidad ya emitida hasta su exp; no prometer revocación instantánea proveedor.

`message-subscribe` puede permitir mensajes recientes previos por rewind incluso sin permiso `history`, según documentación Ably; no afirmar ausencia total de historial del transporte. Por ello los eventos excluyen secretos, credenciales, correo y perfiles privados, y el canal solo contiene notificación mínima autorizada para esos participantes; REST vuelve a autorizar detalle. Los identificadores técnicos mínimos siguen sujetos a política de datos y no se declaran anónimos. No conceder presencia o espectadores por comodidad del SDK. `subscribe` genérico agrupa más operaciones; la compatibilidad de `message-subscribe` en SDK/plan real es POR_VERIFICAR. Si no existe, registrar impacto/propuesta antes de ampliar derechos, sin hacerlo silenciosamente.

| `RateBucket` | Entorno/dueño/operación/sujeto o IP pseudónima/recurso, windowStart/size, count/limit; tiempo DB y actualización atómica |
| `AIComputeGrant` | jti, principalUUID/recurso/base/versiones, canonicalPayloadHash, budgets, issuedAt/deadline≤120s, issued/claimed/completed/expired y claimedAttemptId; completed libera reserva de concurrencia sin permitir nuevo claim; solo Game DB |
| `AIClaimReceipt` | jti/attemptId/hash/budgets/claimedAt/deadline, resultado fijo de admisión; repetirlo no extiende deadline ni autoriza segundo handler |
| `AblyCapabilityGrant` | gameId/canal exacto/clientId/capability/issuedAt/expiresAt, correlación no secreta; ausencia de wildcard/publish/presence/history comprobada |

Operaciones mutantes vuelven a autorizar antes de devolver también un recibo idempotente: conocer commandId no concede el resultado de otro principal. El vínculo G→U no reescribe `(principal original, recurso, commandId)` ni usa U para leer recibos G; historial terminado es una concesión separada de lectura de 07.01/07.03. Requests internos de datos tampoco aceptan un client body como prueba de titular; Identity demuestra fuente/objetivo/operationId y Game autoriza su alcance propio.

Errores de dominio propuestos y categoría para mapeo 05.02:

| Error | Categoría / acción segura |
|---|---|
| `TOKEN_INVALID`, `TOKEN_EXPIRED`, `TOKEN_KEY_UNKNOWN`, `TOKEN_PURPOSE_MISMATCH` | Autenticación rechazada; sin efecto, mensaje seguro sin enumerar secretos/claims privados |
| `AUTH_VALIDATION_UNAVAILABLE` | Dependencia/material no verificable, propuesto 503; no tratar como credencial correcta ni borrar todas las cookies |
| `ORIGIN_REJECTED`, `CSRF_REJECTED` | Mutación rechazada, propuesto 403; ningún fallback a token body o GET |
| `RESOURCE_FORBIDDEN`, `SERVICE_SCOPE_FORBIDDEN` | Falta de permiso de recurso/scope, respuesta sin revelar recurso privado; verificar antes de motor/SQL de efecto |
| `RATE_LIMITED`, `RATE_LIMIT_UNAVAILABLE` | Propuesto 429 con Retry-After seguro o 503 al no poder comprobar límite; sin ejecutar trabajo costoso |
| `AI_GRANT_INVALID`, `AI_GRANT_EXPIRED`, `AI_GRANT_ALREADY_CLAIMED` | No iniciar cálculo; nuevo grant solo por nueva admisión Game, sin segundo efecto del claim |
| `AI_GRANT_CLAIM_UNCERTAIN` | Callback sin resultado confirmado; no cómputo hasta resolver dentro de vigencia, luego cancelar |
| `SESSION_RECOVERY_MARGIN_INSUFFICIENT`, `REFRESH_REUSED`, `REFRESH_ADVANCED` | Semántica exacta de 07.01; renovación/reconciliación/revocación según caso, sin inferir fracaso deportivo |
| `ABLY_PERMISSION_UNAVAILABLE` | No emitir capacidad; REST autorizado puede continuar según dueños, sin token universal |

RFC 9457, códigos HTTP exactos, requestId, payload/error bounds y compatibilidad de rutas pertenecen a 05.02. Tipos/claims/versiones desconocidos se rechazan como incompatibles, sin aceptar una política más amplia para sostener disponibilidad.

## 10. Justificación y alternativas

| Elección propuesta | Motivo y compensación |
|---|---|
| ES256/P-256 y tipos/llaves distintos | Firma pública permite Game local y evita secreto HMAC compartido con todos los validadores; soporte/librerías deben probarse. Otro algoritmo requiere revisar perfil/consumidores |
| aud de usuario solo Identity/Game | Una sesión web consume ambos; no otorga acceso AI/S2S. Tokens por audiencia única reducirían ámbito, a costa de dos cookies/ciclos que no se adoptan ahora |
| Caché fresca máxima 300 s | Acota material observado durante outage/retirada de claves; puede bloquear instancias frías o outage prolongado. Aceptar stale indefinido ocultaría confianza no verificable |
| Refresh con path Identity y acceso host-prefix | Reduce exposición de opacos sin exigir otro origen; Path no protege de XSS mismo origen y `__Secure-` requiere rechazar duplicados/inyección |
| CSRF nonce ligado en JWT/familia + origen | Game verifica localmente y refresh usa su registro sin introspección por jugada; XSS sigue siendo riesgo, SameSite solo no sustituye control |
| Callback link solo acredita U | Conserva capacidad G para activas y elimina cambio de actor silencioso; cambiar contexto requiere login separado/advertido |
| Clave propia por servicio y scopes | Compromiso de AI no obtiene permisos de usuario/Elo; rotación requiere coordinar keyrings/despliegues |
| PostgreSQL y claim IA en Game | Límite funciona entre Functions sin Redis/DB AI; añade round trip/coste y un claim puede perder cómputo por crash. No garantiza entrega/cálculo exactamente una vez |
| message-subscribe exacto + expiry mínimo | Menor capacidad que subscribe genérico; SDK/plan pendiente y rewind puede exponer notificaciones recientes ya autorizadas |

Introspección Identity por movimiento, credencial universal, token sensible en localStorage, publicar desde cliente o actor libre por body contradicen fuente. Redis/cola/outbox/gateway o servicio adicional no son soluciones obligatorias a estas compensaciones; requerirían propuesta/impacto/aprobación dentro de su alcance futuro.

## 11. Ejemplo técnico explicado

Datos sintéticos, **PROPUESTA**, solo Markdown; no son JWT firmado, secreto ni configuración ejecutada. Las URIs `.invalid` son marcadores de entorno, no proveedores configurados:

```json
{
  "header": {"alg":"ES256","typ":"tk-user-at+jwt","kid":"test-access-k2"},
  "claims": {
    "ver":1,
    "iss":"https://identity.example.invalid",
    "aud":["tk-identity","tk-game"],
    "sub":"00000000-0000-4000-8000-000000000001",
    "sid":"synthetic-family-1",
    "jti":"synthetic-access-1",
    "iat":1792576800,"nbf":1792576800,"exp":1792577700,
    "identity_kind":"guest","roles":["guest"],"profile_ready":false,
    "session_recoverable_until":1792749600,
    "csrf_hash":"<base64url-sha256-nonce-sintetico>"
  }
}
```

`exp-iat=900 s` y horizonte `iat+172800 s` reservan margen de 48 h; no se concede JWT de 48 h. Game selecciona política de usuario y su issuer configurado, valida firma/JWKS/aud/tiempo, CSRF/origen y participante; ignora cualquier actor/color declarado por body como autoridad. Conocer el UUID o presentar un JWT Google con el mismo sub no basta. El nonce CSRF no permite autenticar sin cookie de acceso.

```text
Game: autoriza petición AI de G sobre base R
  reserva cuota y grant J(hash H, budgets B, deadline D) -> commit Game
  llama AI con S2S Game/aud AI/scope ai.compute/J/H/B
AI: verifica Game y payload H; genera attempt A interno
  llama Game con S2S AI/aud Game/scope ai.grant.consume/J/H/B/A
Game: CAS issued -> claimed(A), persiste recibo -> respuesta
AI: callback perdido -> mismo handler repite A; mismo recibo, un solo inicio
  replay HTTP al endpoint AI -> handler A2 distinto -> claim rechazado
  crash después de claim -> puede no existir resultado, grant no se libera solo
Game: recomendación para R vuelve -> revalida R/fase/legalidad antes de aplicar

Google link G -> U existente:
  callback acredita U en LinkProof; cookies G permanecen
  confirmar vínculo -> historial terminado, activa G no cambia
  login U posterior requiere intención explícita separada; sin linkedSubjects
```

No hay transacción abierta entre HTTP/AI y la mutación deportiva. Claim de cuota no equivale a jugada confirmada. Los parámetros de búsqueda/formatos definitivos serán consumidores del dominio 08, manteniendo límites autorizados y sin medir fuerza por este ejemplo.

## 12. Casos límite, fallos y seguridad

| Situación | Comportamiento exigido por esta propuesta |
|---|---|
| JWT firma incorrecta, none/HMAC/otro alg, JSON duplicado o kid inválido | Rechazar sin consultar clave arbitraria ni ejecutar motor |
| Firma correcta, issuer/aud/typ equivocados | Rechazar aunque exista UUID/rol válido; Google/servicio/Ably no sustituyen producto |
| JWT antes de nbf o después de exp+tolerancia | Rechazar; renovar por Identity, no ampliar access por caída proveedor |
| kid desconocido con jku/x5u/jwk inyectado | No fetch a URL cliente ni aceptar clave embebida; política fija y rechazo seguro |
| Identity caído, clave conocida fresca | Verificación local hasta primer límite snapshot/token/margen; sin consulta Identity por movimiento |
| Identity caído, instancia fría/caché vencida | Fallo de validación no disponible, sin aceptar firma sin verificar |
| Rotación K2 y caché vieja | Fetch acotado o rechazo; prepublicación ayuda disponibilidad, no bypass |
| Logout/reutilización y JWT anterior válido | No renovar; token previo puede actuar hasta caducidad/permiso recurso según fuente; capacidad Ably tampoco instantáneamente revocada |
| Origen subdominio, null, ausente o cabecera CSRF inválida | Mutación navegador rechazada; callback GET solo por excepción completa correlacionada |
| Cookie duplicada, path/domain ambiguo o request de upstream directo | Rechazar ambigüedad y exigir misma autenticación/origen configurado; no confiar en rewrite como permiso |
| Refresh confirma sin respuesta, padre luego vence | Proof retenida permite recibo coincidente vigente antes del rechazo por padre; mismos exp/horizonte, no nueva rotación |
| Link callback U existente mientras G tiene activas | Conservar cookies G y guardar prueba U limitada; no login U automático, tampoco si U es rival activo |
| Usuario válido ajeno o admin sin permiso de recurso | No mover/ver detalle/suscribir; rol no sustituye participación, turno, fase/revisión o política de datos |
| Credencial Game→AI presentada a Game o AI→Game en operación de partida | Aud/scope/tipo impiden uso cruzado; AI solo consume grant, nunca mueve ni altera Elo |
| Contadores concurrentes en varias Functions | Transacción del dueño decide límite global; reiniciar instancia no reinicia cuota |
| DB de cuotas/claim no disponible | No admitir operación costosa/mutante; Game preserva datos ya confirmados, AI no calcula por timeout |
| Callback grant confirma y respuesta se pierde | Mismo handler/attempt puede recuperar recibo vigente; no segundo cálculo ni otro handler autorizado |
| Crash AI después de claim o replay con attempt nuevo | Grant consumido; resultado puede perderse, nueva admisión acotada o fallback futuro, sin liberar por suposición |
| Payload/budgets/grant alterados, jti expirado o hash discordante | Rechazar antes de calcular/claim; no confiar en intención de cliente ni jti aislado |
| Ably capacidad sin campo/namespace wildcard/publicación | No emitir; verificar permiso efectivo y expiry; nombre de canal no autoriza recurso |
| message-subscribe sin history pero rewind entrega reciente | Notificaciones mínimas no secretas y autorizadas; no afirmar que history ausente impide todo mensaje previo |
| Private key/recibo perdido, keyring de otra preview o reloj fuera de política | Falla segura y evidencia sanitizada; no copiar producción/aceptar otra audiencia para «arreglar» disponibilidad |

XSS o compromiso de servidor pueden utilizar credenciales de ese contexto; HttpOnly/CSRF no acreditan inmunidad. Logs redactan secretos desde borde/transportes, incluyendo errores y cabeceras. La mitigación de compromiso/rotación operativa requiere 10.01/10.04 y autorización; esta misión no ejecuta ningún incidente o cambio externo.

## 15. Observabilidad, secretos, migración y recuperación

Propuesta de secretos por entorno/proyecto: privada de acceso solo Identity; privada S2S propia de cada servicio; públicas receptoras/keyrings sin privadas; clave de cifrado de recibos/intentos solo Identity; credenciales DB solo su dueño; API keys Ably solo Game con propósito separado; client secret Google solo Identity. No se copian producción a previews, repo, artifacts de ejemplo, frontend, URL, localStorage o logs. Inyección mediante secretos de entorno previstos, acceso mínimo y revisión de entregas; disponibilidad concreta de controles Vercel/rotación sigue POR_VERIFICAR en 10.01, sin KMS/servicio adicional obligatorio.

Rotación ordinaria propuesta: generar material fuera del repo bajo permiso futuro → distribuir públicas receptoras/prepublicar → verificar compatibilidad en entorno sintético → activar nueva privada → observar ausencia de emisión antigua → retirar privada vieja y luego pública tras solapamiento. Clave de cifrado de recibos mantiene capacidad de descifrar sobres vigentes hasta máximo 48 h o reenvuelve autenticadamente esos sobres antes de retirarla; no confundir vida JWT de 15 min con retención del recibo. Un compromiso obliga a evaluar invalidación deliberada de sesiones/recibos y su impacto recuperable; no preservar una privada comprometida por disponibilidad.

Observabilidad sanitizada: política/entorno, código de error, kid permitido, edad snapshot/fetch result, expiración/margen sin token, scope/operación, permiso recurso agregado, rate bucket pseudónimo, jti grant/attempt interno y resultado claim, estado de recibo y dependencias. Acceso restringido a identificadores de sujeto/recurso; retención/minimización en 10.02/07.03. Nunca JWT/cookies/Authorization, proof, nonce CSRF, code/state/verifier, privada/API key, payload completo de perfil/exportación o IP en claro. Distinguir 401/403/429/503 en métricas sin revelar existencia privada.

Fallback de autenticación: refrescar desde dueño cuando disponible; no cambiar issuer/aud/alg o aceptar token Google porque JWKS falla. Si Ably falla, REST autoriza normalmente; si Identity falla, acceso/caché vigentes limitan continuidad; si DB de cuotas/claim falla, no iniciar mutación/cálculo. Claves/caches expiran por política y no por cron; un proceso de limpieza no determina vigencia. No hay RPO/RTO, latencia, resistencia DDoS o entrega observados.

Migración de perfil JWT exige compatibilidad explícita de todos los receptores y límite de coexistencia; `ver` desconocida rechaza. Cambiar tipos/emisores/scopes/cookie paths requiere revisión de consumidores y estrategia de borrar cookies antiguas sin ambigüedad. Rollback no vuelve válidos refresh consumidos, grant reclamados o issuer revocado. La operación futura de incidentes/backups pertenece a 10.03/10.04 y no se ejecuta aquí.
