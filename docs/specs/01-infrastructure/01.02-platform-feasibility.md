## 5. Invariantes y entidades

- Cuatro proyectos: web Next.js y exactamente Identity, Game, AI Go/Gin, autónomos. El motor único versionado se comparte por importación; no se convierte en servicio nuevo ni se duplica en TS.
- PostgreSQL es autoridad persistente; Identity y Game tienen propiedad separada, sin SQL cruzado. AI no tiene DB inicial y ninguna Function guarda sesiones/partidas/idempotencia únicamente en RAM.
- Una jugada aceptada confirma comando, movimiento, efectos y estado de Game en una transacción. Publicar Ably ocurre después; su fallo no deshace un commit confirmado.
- Ably Free comunica avisos mínimos; REST recupera estado oficial. No se presupone entrega exactamente una vez, outbox duradero ni WebSocket propio persistente.
- Datos, roles, claves y OAuth de integración/previews no comparten producción. Las cuotas pueden agregarse por cuenta aunque se separen aplicaciones/entornos.
- Documentación oficial consultada y compatibilidad experimental observada son evidencias distintas. Runtime beta, módulos compartidos, región, cuota efectiva y viabilidad siguen `POR_VERIFICAR` hasta la prueba autorizada.

Entidades: caso experimental, artefacto/build, proyecto, propietario de datos, conexión agrupada/directa, entorno, evidencia y decisión go/no-go.

## 10. Justificación y alternativas

La PoC precede a la implementación completa porque runtime beta, contexto de módulos, DB y fallos postcommit pueden invalidar el plan aunque cada proveedor documente una capacidad por separado. PostgreSQL y roles conservan autoridad y durabilidad sin exigir procesos persistentes. Pool agrupado y conexión directa tienen fines distintos; no son intercambiables por simplicidad.

Alternativas `PROPUESTA` si falla empaquetado: incluir dependencias compartidas en un contexto admitido, distribuir módulos versionados o vendoring reproducible, manteniendo una única fuente del motor. Cada opción exige repetir builds y controles de versión. Si ninguna satisface arquitectura/coste, registrar `NO-GO` y presentar impacto/alternativas al propietario; no sustituir Vercel, fusionar servicios, añadir Redis o contratar pago unilateralmente.

## 11. Ejemplo mínimo explicado

Secuencia conceptual, solo Markdown y sin comandos de producto ejecutados:

```text
comando K, versión V → autenticar/autorizar → bloquear partida
  → si K ya confirmó: devolver resultado persistido equivalente
  → validar V y movimiento con motor E
  → transacción: K + movimiento + efectos + estado V+1 → COMMIT
  → intentar aviso Ably V+1
si aviso falla: conservar commit; cliente consulta REST → V+1
si respuesta se pierde: reintentar K → mismo efecto y resultado oficial
```

K repetido con contenido diferente se rechaza; una clave nueva sobre V obsoleta no genera una segunda jugada. La persistencia de K debe sobrevivir al reinicio de una Function. La ventana entre commit y publicación es un riesgo reconocido y REST es recuperación, no una garantía ficticia de publicación eventual.

## 12. Fallos, límites, seguridad y recuperación

No se usan locks de sesión dependientes de una conexión persistente del pooler; el diseño de transacción bloquea la partida dentro de la transacción y controla versión/idempotencia. [Neon pooling](https://neon.com/docs/connect/connection-pooling), consultado el **2026-10-21**, documenta pooling transaccional y distingue uso agrupado en serverless frente a conexión directa para herramientas de migración. El modo elegido debe probarse con pgx; no se presupone que un pool con gran admisión de clientes equivalga a capacidad ilimitada de DB.

Sin DB disponible no se responde jugada aceptada. Si el resultado del commit es incierto tras timeout, reconsultar/reintentar idempotentemente antes de informar un estado definitivo. Ably caído o aviso duplicado/fuera de orden conduce a reconciliación REST sin revertir movimientos. Reinicios y paralelismo no pueden invalidar sesiones por perder RAM; credenciales de preview no permiten producción. CORS/cabeceras del cliente no prueban confianza interservicios. La cancelación IA descarta trabajo obsoleto y Game revalida cualquier respuesta tardía.

La documentación [Ably Free](https://ably.com/docs/platform/pricing/free), consultada el **2026-10-21**, presenta el paquete para experimentación/PoC. Su adecuación al lanzamiento permanece `POR_VERIFICAR`; la recuperación REST no permite declarar equivalente una ausencia prolongada de multiplayer sin revisar requisitos.
