## 2. Objetivo, alcance y valor

Definir una organización revisable que permita construir web, Identity, Game y AI por separado, compartir contratos y un único motor Go y conservar ejecución local. Abarca stack, dependencias, módulos y plan de desarrollo; no crea código, manifiestos, configuraciones ni entornos. Las elecciones sirven al MVP base y ampliado del lanzamiento comprometido, sin aplazar IA, clasificación ni estadísticas por conveniencia técnica.

Esta spec concreta decisiones existentes. Sus rutas candidatas permiten revisar fronteras antes de implementar; no acreditan que un build funcione ni autorizan instalaciones, servicios o despliegues. El permiso vigente está en [AGENTS](../../../AGENTS.md) y [PLANS](../../../PLANS.md).

## 5. Invariantes y entidades

- Existen exactamente tres microservicios de dominio: Identity, Game y AI. La web es el cuarto proyecto de despliegue; los paquetes compartidos no son servicios.
- Identity posee identidad/sesiones/perfiles; Game posee partidas, movimientos, resultados, Elo y agregados; AI comienza stateless, sin DB ni facultad de confirmar jugadas.
- Game y AI importan un único motor Go puro, determinista y versionado. Web recibe legalidad y previsualizaciones por API; TypeScript no implementa otro reglamento.
- Cada servicio tiene módulo y build autónomo. Compartir motor o contratos no comparte repositorios SQL ni autoriza importaciones entre los interiores de servicios.
- Las dos propiedades de datos Identity/Game permanecen separadas, sin SQL cruzado; la elección física de bases/esquemas sigue pendiente. Ni una sesión ni una partida tienen la RAM de una Function como almacenamiento persistente.
- Local es un modo de juego en un dispositivo; no equivale a offline. Compose describe desarrollo y no crea un cuarto servicio de dominio ni un requisito de alojamiento.

Entidades de diseño: unidad desplegable, módulo Go, paquete TypeScript, contrato, motor/versiones y entorno. No se define aquí el modelo completo de una partida ni tablas de producto.

## 7. Diseño de componentes y responsabilidades

Mapa de rutas `PROPUESTA`, pendiente de revisión del diseño y de 01.02; ninguna de estas rutas de producto se crea ahora:

| Ruta candidata | Unidad y dependencias permitidas |
|---|---|
| `apps/web` | Next.js/React/TS; cliente HTTP y tipos generados; presentación HTML accesible y R3F. Sin conexión a DB ni motor de reglas TS. |
| `services/identity` | Módulo Go autónomo; transporte Gin → aplicación → dominio; adaptadores de Identity DB y proveedores de identidad. |
| `services/game` | Módulo Go autónomo; Gin → aplicación → motor; adaptadores de Game DB, Identity HTTP, AI HTTP y Ably. |
| `services/ai` | Módulo Go autónomo; Gin → búsqueda acotada → motor. Sin repositorio SQL ni publicación oficial de movimientos. |
| `modules/engine` | Módulo Go compartido, puro y versionado; no importa servicios, Gin, pgx o SDK Ably. |
| `contracts/http` y `contracts/events` | Fuentes de OpenAPI/JSON Schema; validación y generación fijadas en implementación futura. |
| `modules/contracts` y `packages/contracts` | Tipos/validadores Go y TS generados; artefactos de transporte, separados del estado interno del motor. |
| raíz del repositorio | Workspace pnpm y go.work para desarrollo; herramientas y manifiestos solo tras autorización futura. |

Las capas internas candidatas son `transport`, `application`, `domain` y `adapters`, con el equivalente de visibilidad `internal` cuando proceda. Ninguna dependencia va desde el motor hacia esas capas. Identity no importa Game; Game consulta perfiles por API y nunca importa el adaptador SQL de Identity. AI recibe el estado/contexto reglamentario autorizado mediante contrato y devuelve una propuesta; Game conserva versión, validación y commit.

En local, go.work puede enlazar los módulos de servicios, motor y contratos; pnpm enlaza los paquetes TS. En el build aislado cada servicio necesita resolver sus dependencias desde su raíz efectiva sin depender de la máquina del desarrollador, cachés o rutas absolutas. `PROPUESTA`: evaluar en 01.02 inclusión controlada del módulo compartido dentro del contexto de build y referencias de módulo fijadas; no prescribir `replace` relativo como solución probada. La distribución de módulos públicos/versionados o vendoring son alternativas revisables si se requieren, sin duplicar la fuente del motor.

El desarrollo local futuro contempla procesos nativos de web/servicios y PostgreSQL con dos propietarios y credenciales distintas en Compose; auxiliares de observabilidad locales solo cuando sean necesarios. No se incorpora Redis ni un gateway WebSocket preventivamente. La web local puede usar servicios Go locales; las partidas local/práctica continúan dependiendo del motor del backend.

## 8. Contratos, tipos, errores y versionado

| Frontera | Campos o regla de contrato |
|---|---|
| HTTP | OpenAPI 3.1, `/api/v1`; esquemas de petición/respuesta con tipos, requeridos, límites y errores. Las rutas concretas y paginación pertenecen a 05.02. |
| Eventos | `schemaVersion`, `gameId`, `version`, `type` y carga mínima semántica; validadores Go/TS; sin comandos de animación ni secretos. Detalle canónico en 05.04. |
| Motor | Estado lógico + movimiento + contexto reglamentario necesario → nuevo estado + eventos + error tipado, sin mutar entrada. Versiones de estado, reglamento y registro diferenciadas por dominio 03. |
| Error HTTP | Problem Details RFC 9457 con `type`, `title`, `status`, código de dominio y `requestId`; mensajes seguros. No convertir un fallo interno en jugada aceptada. |
| Dependencia | Identidad de módulo, versión fijada y consumidor explícito. Un cambio incompatible exige nueva versión/política de transición y revisión de Game/AI/web. |

Los DTO generados son transporte, no propiedad compartida de tablas. La validación de entrada en ejecución permanece obligatoria aunque compile TypeScript. El contrato público no acepta un tablero del cliente como verdad competitiva. Un generador no produce reglas del juego. Autorización, idempotencia y errores concretos se detallarán en [05.02](../../index.md#spec-05-02) y [05.03](../../index.md#spec-05-03), `PENDIENTE_LOTE_3`; no se inventa su cierre aquí.

## 10. Justificación y alternativas

Go/Gin y Next.js/React/TS conservan las elecciones aprobadas y separan autoridad y presentación. pnpm/go.work facilitan trabajo del monorepo sin exigir que cada build despliegue todos los proyectos. El motor compartido limita divergencias de legalidad, a cambio de coordinar versiones y reproducción histórica. Generar contratos reduce discrepancias de forma, pero exige validación y pruebas semánticas.

Alternativas `PROPUESTA`, no adoptadas: módulo compartido distribuido por versión o vendoring para builds aislados si 01.02 demuestra necesidad; presentan costes de publicación/actualización y riesgos de empaquetar versiones distintas. Un monolito, cuarto servicio, motor TS, gateway Socket.IO o dependencia obligatoria de Redis contradicen decisiones vigentes y exigen cambio aprobado. No se elige otra plataforma para eludir un build fallido.

## 11. Ejemplo mínimo explicado

Ejemplo documental de dependencias, sin archivos de producto creados y sin identificadores de módulos públicos inventados:

```text
web --HTTP y tipos TS generados--> Identity / Game
Game --HTTP protegido--> AI
Game ----importa versión E----> motor Go puro
AI ------importa versión E----> motor Go puro
Identity --SQL propietario--> Identity DB
Game -----SQL propietario--> Game DB
Game --tras commit--> Ably --aviso--> web --REST--> Game
```

La misma `E` exige equivalencia efectiva del motor en ambos builds; un número declarado no demuestra que el artefacto contenga esa revisión. Ably avisa de una versión confirmada; el cliente recupera la verdad por REST. AI no aparece conectado a ninguna DB.

## 12. Fallos, límites, seguridad y recuperación

Un build que solo funciona con go.work o caché local bloquea factibilidad; se conserva el diseño y se recoge evidencia antes de proponer empaquetado distinto. Un contrato generado desactualizado bloquea integración y se corrige desde su fuente, evitando editar dos copias manuales. Un servicio que importa interiores de otro se devuelve a revisión de fronteras.

Secretos de DB, OAuth y Ably quedan en entorno autorizado, sin prefijos públicos de Next ni logs/ejemplos; los clientes no reciben credenciales SQL ni capacidad de publicación oficial. Los entornos y roles se separan en 01.02. RAM puede contener datos efímeros acotados, nunca el único registro de sesión, partida o idempotencia. Un reinicio de Function no puede convertir una operación no confirmada en aceptada. No hay migraciones de producto que ejecutar en esta misión.
