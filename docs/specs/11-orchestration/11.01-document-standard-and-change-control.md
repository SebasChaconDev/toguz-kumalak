## 2. Objetivo, alcance y valor

Definir un formato y un proceso de cambio que permitan convertir decisiones aprobadas en documentos ejecutables por una sesión futura sin inventar arquitectura ni atribuir evidencia inexistente. El alcance presente es exclusivamente la generación y revisión de los 31 Markdown autorizados del lote 1 del [inventario](../../index.md#inventario). El inventario aprobado contiene 81 rutas, incluidas 40 especificaciones; su aprobación no autoriza escribir los lotes 2–6 ni aprueba su contenido.

Se excluyen implementación, pruebas de producto, instalaciones, archivos no Markdown, servicios, recursos externos, secretos y mutaciones Git. Los ejemplos se conservan dentro del Markdown. Los requisitos de calidad del producto se describen para una autorización futura; no se ejecutan como parte de la auditoría documental.

Una ADR propuesta no modifica una decisión aprobada. Una especificación `EN_REVISIÓN` no desplaza una fuente superior.

## 5. Invariantes y entidades documentales

- Cada ruta e ID del inventario identifica un documento; no se reutilizan IDs ni se crean rutas fuera de la autorización.
- El texto de cada decisión `PRE-NN.Xn` se conserva en registro y copia del maestro; las specs añaden interpretación trazable sin reescribir ese texto.
- Los estados documentales son `BORRADOR`, `EN_REVISIÓN`, `APROBADO`. Las naturalezas de afirmación son `APROBADO`, `POR_VERIFICAR`, `PROPUESTA`. Son ejes independientes: un requisito aprobado puede estar en una spec todavía en revisión.
- `APROBADO` como estado documental requiere evidencia humana que identifique el contenido revisado. El propio autor no aprueba su documento.
- La autorización de trabajo se informa por separado: `LOTE_1_EN_CURSO` durante redacción y `LOTE_1_EN_REVISION` al entregar. El inventario `APROBADO` no convierte el producto en implementado ni permite comenzar otro lote.
- Un enlace a una entrega futura lleva al ancla de su entrada existente en el índice y se etiqueta `PENDIENTE_LOTE_N`; no se fabrican documentos vacíos para resolverlo.
- Toda afirmación empírica identifica evidencia observada o se etiqueta `POR_VERIFICAR`. Decisión aprobada, ejemplo y plan no son prueba de integración.

Las entidades mínimas son documento, decisión fuente, ADR, conflicto, vínculo de trazabilidad, evidencia y aprobación. Sus contratos se definen en §8; no son entidades de una base de datos de producto.

## 6. Requisitos funcionales y no funcionales

| Requisito | Regla y prioridad |
|---|---|
| DOC-01 | Cada spec contiene las 17 partes de §6 del maestro o declara `NO_APLICA` con motivo concreto. Obligatorio para documentos base y ampliados. |
| DOC-02 | Requisitos y AC citan fuente exacta y dueño canónico. No se ocultan requisitos ampliados para reducir el lanzamiento comprometido. |
| DOC-03 | Contratos describen campos, límites, errores, versión y autoridad según el módulo; no se rellenan con APIs ficticias las specs de gobierno. |
| DOC-04 | README distingue objetivo, arquitectura decidida, desafíos, pruebas previstas y demo prevista de resultados realmente observados. |
| DOC-05 | Cambios relevantes requieren propuesta e impacto, ADR cuando alteren arquitectura/decisiones y aprobación humana antes de aplicarse como requisito. |
| DOC-06 | Texto legible por separado con dependencias explícitas; enlaces relativos verificables, fences cerrados, IDs únicos y vocabulario común. |
| DOC-07 | Correcciones editoriales dentro de rutas autorizadas pueden integrarse conservando significado; no habilitan nuevos permisos ni cambios semánticos. |
| DOC-08 | No se añaden cuarto servicio, motor TypeScript, Redis/Socket.IO obligatorios, gasto ni capacidad offline por inferencia. |

El estándar se aplica por igual a MVP base y ampliado. La diferencia entre hitos organiza el trabajo; ambos forman parte del lanzamiento comprometido. Los controles documentales son condiciones de revisión, no pruebas de producto ni metas de rendimiento medidas.

## 7. Diseño del proceso y responsabilidades

```text
Propietario: autorización y decisiones
  ↓
Maestro + registro + inventario aprobado
  ↓
11.01: formato, trazabilidad y cambios
  ↓
Autores: documentos propios → revisión documental → coordinación: integración
  ↓
Informe de lote → propietario: revisión → gate o devolución con cambios
```

El registro conserva decisiones; ADR explica por qué y alternativas; specs concretan contratos y aceptación; AGENTS resume límites operativos; planes ordenan trabajo. El índice identifica rutas y estado; la matriz conecta requisito con dueño canónico, fase, componentes, verificación y evidencia. Las referencias cruzadas evitan duplicar autoridad. La coordinación integra índices, cobertura y conflictos; la asignación detallada se desarrolla en el consumidor 11.02.

## 8. Contratos de información y control de cambios

| Entidad | Campos mínimos y validación |
|---|---|
| Documento | `id`, `ruta`, `dominio`, `version`, `fecha`, `estado_documental`, `owner`, `lote`; ID/ruta deben coincidir con inventario. Fecha ISO y versión explícita. |
| Fuente | `decision_id`, `enlace_registro`, `seccion_consumidora`, `naturaleza`; ID exacto existente, sin normalizar a una abreviatura ambigua. |
| ADR | ID incremental inventariado, estado, contexto, decisión, alternativas, motivo, consecuencias, fuentes y evidencia de aprobación cuando exista. |
| Cambio relevante | Documento/decisiones afectados, discrepancia, impacto, alternativas, propuesta, aprobación requerida, estado y evidencia. Se registra en [conflictos](../../conflicts.md) y ADR pertinente, sin crear nuevas rutas no aprobadas. |
| Trazabilidad | Requisito → spec canónica → fase prevista → componentes previstos → pruebas previstas → evidencia real o pendiente → estado; mantener en [matriz](../../traceability.md). |
| Aprobación | Texto humano, alcance del lote/contenido y fecha; si hay ambigüedad no elevar el estado ni iniciar trabajo dependiente. |

Autenticación HTTP, paginación y eventos de red: `NO_APLICA`, porque este contrato es un registro Markdown. Autoridad documental: propietario para aprobar, autor para redactar, coordinación para integrar. Versionar el contenido mediante versión/fecha y registro de cambio en los Markdown autorizados; la misión actual no autoriza commits. La integración es idempotente cuando conserva un único ID y una única fila canónica por requisito, en vez de duplicarlos al reintentar.

## 9. Metodología para sesiones futuras autorizadas

1. Consultar permiso vigente y rutas del inventario antes de escribir. Esto impide confundir un plan futuro con autorización actual.
2. Leer fuentes exactas y dependencias; identificar dueño canónico de cada requisito antes de redactar. Así se evita definir contratos incompatibles.
3. Completar las 17 partes según §11, marcando preguntas y pruebas pendientes. El detalle debe permitir actuar sin escoger arquitectura por cuenta propia.
4. Registrar cualquier discrepancia con impacto y alternativas; mantener la decisión fuente. En reglas del juego, bloquear el cierre del algoritmo afectado hasta resolución humana.
5. Revisar texto, enlaces, cobertura y coherencia con consumidores. Si cambia un contrato compartido, revisar todos los consumidores identificados antes del gate.
6. Integrar versión, índice y trazabilidad; enumerar cambios y evidencia observada. No elevar `POR_VERIFICAR` por completar una plantilla.
7. Entregar lote `EN_REVISIÓN`, pedir su gate y detenerse. «APRUEBO LOTE 1» registra revisión del lote; el permiso de trabajo posterior depende de la instrucción humana correspondiente, sin iniciar automáticamente lote 2.

Estos pasos describen continuidad documental futura. Implementar el producto requiere otra autorización expresa, aunque toda la documentación llegara a aprobarse.

## 10. Justificación y alternativas

| Elección | Motivo, alternativa y compensación |
|---|---|
| Dos ejes de estado | Impide tratar requisitos decididos como implementaciones probadas. Un único campo sería más breve, pero mezcla autorización, revisión y evidencia. |
| Fuente canónica y enlaces | Conserva la voluntad del propietario. Copiar el registro en cada spec facilitaría lectura aislada, pero multiplicaría divergencias. |
| Índice para archivos futuros | Mantiene enlaces verificables sin simular entregables. Los archivos vacíos ocultarían el trabajo pendiente y excederían el lote. |
| AC con evidencia | Hace la revisión repetible. Una lista de «completado» por el agente carece de prueba independiente. |
| Cambio relevante con aprobación | Protege alcance y arquitectura frente a preferencias. La edición directa ahorra un paso, pero elimina el control humano. |

No se imputa coste monetario a este proceso ni se presume una herramienta de auditoría instalada. Las automatizaciones futuras deberán justificarse y autorizarse si requieren archivos o dependencias adicionales.

## 12. Casos límite y fallos

- Una corrección aparente cambia una regla, proveedor o alcance: tratarla como cambio relevante, conservar la fuente y detener ese cierre hasta aprobación.
- Un autor aporta solo un resumen de otra sesión: exigir enlaces al registro y evidencia; el resumen no reemplaza la fuente.
- Un enlace futuro no resuelve: corregirlo al ancla del índice con lote pendiente, sin crear el destino.
- Una verificación automática pasa y la semántica contradice una decisión: el documento sigue bloqueado para cierre; el chequeo de formato no prevalece.
- Una afirmación incluye secretos o datos personales innecesarios: excluirlos del ejemplo y de la evidencia publicada; la misión no permite emitir ni copiar credenciales.
- Dos autores modifican la misma ruta o una dependencia cambia mientras se revisa: pausar integración y reasignar propiedad; repetir solo controles afectados tras reconciliar.

Rendimiento del producto, reconexión de red y accesibilidad del tablero: `NO_APLICA` como prueba de este módulo; se revisa que sus requisitos no desaparezcan en documentos consumidores.

## 13. Estrategia de auditoría documental

Sin instalar herramientas ni crear verificadores en disco, enumerar rutas y analizar Markdown en memoria. Contrastar inventario de 81 entradas, 40 specs y subconjunto de 31 archivos del lote 1; no exigir que existan físicamente los lotes posteriores. Comprobar unicidad de IDs, destinos y anclas de enlaces, fences, 17 partes, referencias `PRE-NN.Xn`, cobertura canónica y estado `EN_REVISIÓN`. Revisar semánticamente autoridad, restricciones, riesgos y afirmaciones empíricas.

Ejemplo de procedimiento de auditoría, no ejecutado por aparecer aquí:

```text
leer inventario y permiso vigente
enumerar archivos reales sin escribir
comparar rutas modificadas con Markdown autorizado del lote
comprobar IDs, anchors, links, fences, secciones y cobertura en memoria
revisar que ningún APROBADO documental carezca de aprobación humana
revisar fuentes y contratos compartidos, además de la sintaxis
consultar: git --no-optional-locks status --short
consultar: git --no-optional-locks diff --check
informar resultados reales y límites; no ejecutar producto
```

Los comandos Git solo proceden si existe repositorio y no alteran índice ni configuración. No sustituyen la inspección de archivos nuevos no seguidos. Pruebas unitarias, integración, E2E y benchmarks de producto: `NO_APLICA` en esta misión; sus estrategias se documentan en sus specs futuras.

## 15. Observabilidad, corrección y rollback documental

El informe del lote identifica rutas creadas/modificadas, fuentes cubiertas, verificaciones realizadas, límites, dependencias, conflictos y pendientes. Los contadores describen documentos y decisiones; no son métricas de producto. Conservar versión, fecha y evidencia de aprobación en los documentos autorizados facilita reconstruir qué contenido se revisó.

Ante regresión editorial, el dueño corrige el archivo autorizado y la coordinación actualiza enlaces/matriz afectados. Ante cambio semántico, no presentar la corrección como aprobada sin decisión humana. Rollback documental significa recuperar el texto anterior conocido y registrar motivo/impacto mediante edición de Markdown autorizado; no ejecutar `git reset`, commits ni restaurar archivos ajenos. No hay despliegue ni migración de datos de producto en esta spec.

## 16. Riesgos y cuestiones por verificar

| Riesgo o cuestión | Tratamiento y validación posterior |
|---|---|
| Cobertura aparente por menciones sin contenido | Revisar que cada decisión tenga dueño y tratamiento suficiente; contrastar matriz y spec. |
| Fuentes normativas del juego discrepantes | Registrar conflicto y bloquear cierre del algoritmo; resolver con propietario y fuente oficial antes de especificarlo como definitivo. |
| Precios, runtime y proveedores cambiantes | `POR_VERIFICAR`; exigir fuente oficial fechada y prueba futura autorizada donde corresponda. |
| Deriva entre decisiones y documentos | Auditar referencias y consumidores tras cada cambio relevante. |
| Aprobación sin alcance claro | Mantener estado en revisión hasta aclaración humana; no ampliar autorización por inferencia. |

No hay dependencia externa necesaria para aplicar este estándar de texto. Un fallo en una herramienta de auditoría se informa y se cubre mediante inspección disponible; no habilita instalaciones.

## 17. Evidencias de cierre y trazabilidad

Cerrar la revisión documental exige resultados reales de auditoría estructural y semántica, inventario contrastado, cobertura en [trazabilidad](../../traceability.md), conflictos explícitos y aprobación humana del contenido. Esta versión permanece `EN_REVISIÓN`; su existencia y sus ejemplos no acreditan producto probado o desplegado. El informe coordinado del lote será la ubicación de los resultados ejecutados, sin confundir esta estrategia con un registro de ejecución.

El futuro cierre de implementación exige las pruebas observadas pertinentes del módulo, aceptación, revisión y evidencia, según [11.03](../../index.md#spec-11-03), `PENDIENTE_LOTE_5`; no puede darse por satisfecho mediante una auditoría Markdown.
