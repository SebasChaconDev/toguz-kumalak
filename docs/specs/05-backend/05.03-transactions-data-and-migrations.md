## 2. Objetivo, alcance y valor

Definir cómo guardar una sola decisión oficial aun con solicitudes simultáneas, varias partidas de un jugador, reinicios y respuesta perdida. El contrato debe impedir un movimiento parcial, dos cierres/Elo, SQL cruzado y reutilización de una intención cuyo resultado se desconoce.

Incluye modelos relacionales Identity/Game, snapshot JSONB versionado, consultas tipadas, unidad transaccional, idempotencia, recuperación/actividad, grants/cuotas, procesos de datos y migraciones. AI permanece sin DB inicial. Se conserva todo el lanzamiento base y ampliado; fórmulas/visibilidad/retención de datos se concretan en sus dueños, sin reducir alcance ni inventar reglas deportivas.

Esta misión solo produce Markdown conforme a [AGENTS](../../../AGENTS.md)/[PLANS](../../../PLANS.md#lote-3). No se crean SQL, Go, manifiestos o migraciones ejecutables; no se instalan herramientas, conectan bases/proveedores, ejecutan pruebas de producto o despliega infraestructura.

## 5. Invariantes y entidades

- Un commit Game aceptado contiene intención/receipt, movimiento si existe, eventos semánticos, estado/contexto y todos los efectos obligatorios del cierre. Si falla alguno, no se confirma ninguno.
- Cada partida tiene como máximo un resultado; cada efecto Elo por `(gameId,playerId)` se aplica una sola vez. Solo ranked explícita entre dos registrados elegibles al inicio produce Elo. Local, IA, práctica, casual, invitado e inconclusa no lo producen; vínculo posterior no reclasifica.
- Dos finales de partidas diferentes que comparten jugador leen/modifican sus ratings actuales bajo locks comunes. El rating al inicio de una partida no se usa como rating al finalizarla.
- Identity SQL solo contiene su propiedad; Game no consulta Identity SQL ni tiene FK a sus tablas. AI no recibe DSN/rol DB. No existe transacción ACID distribuida Identity/Game/Ably/AI.
- Todo escritor Game participa en la misma jerarquía de guardas/locks, incluidos join/start, movimientos/cierres internos, heartbeat, vínculo, barrera/limpieza, reconstrucción y purga. Una ruta administrativa no puede eludirla.
- `gameRevision`, `moveOrdinal`, `activityVersion`, `ratingSequence` y versiones de esquema son ejes distintos. JSON transporta uint64 como decimal string; no se usa bigint firmado para prometer todo ese rango.
- Repetición cuenta inicial una vez y movimientos completos confirmados con salida activa. No cuenta duplicados, simulación, preview, heartbeat, ofertas, renuncia, acuerdo o terminales. Reclamación R-07 por cualquiera de ambos participantes revalida ventana/revisión/historia atómicamente.
- Retirar PII o receipt privado no permite reutilizar una clave ya decidida. UUID/digests/tombstones son datos potencialmente pseudónimos, no anonimización demostrada.

## 7. Diseño relacional, locks y pipeline

### Propiedad y disposición propuesta

`PROPUESTA` inicial para [RISK-09](../../conflicts.md#risk-09): dos bases PostgreSQL lógicas `identity` y `game`, con roles de aplicación/migración distintos por base y entorno; AI sin base/rol. Si cuotas verificadas obligaran a comparar esquemas separados, se revisa antes de adoptar esa alternativa, preservando grants/propiedad y pruebas de denegación. No se elige cantidad de proyectos Neon, región o plan de pago. En ambos casos se deniega acceso a propiedad ajena, se fija search_path seguro y no se instala una extensión que habilite SQL cruzado.

Tipos comunes propuestos: UUID para claves de entidad; timestamptz UTC para instantes; `numeric(20,0)` con CHECK0..18446744073709551615 para revisión/ordinal/secuencia uint64; enums de aplicación con CHECK explícito; JSONB de forma conocida. Go convierte numeric mediante tipo/override sqlc comprobado, sin float64 ni truncar a int64. Rating/precisión/redondeo tienen versión de política de07.04; no se fijan por elegir tipo de almacenamiento.

La escala0 de numeric puede redondear una entrada fraccionaria antes de aplicar CHECK; no es un validador de la forma original. El parser tipado Go debe rechazar fracciones, signos/ceros no canónicos y overflow antes de enviar el valor, y verificar el mapping al leer. El fragmento SQL no acredita por sí solo ese rechazo de transporte.

CHECK/UNIQUE/FK protegen dominios locales/unicidad, no prueban automáticamente historia, suma162 o elegibilidad entre varias filas. Go valida estado completo/versiones/invariantes antes de serializar JSONB y al leer; la misma transición genera columnas espejo (turn/terminal/revisión) y snapshot. Fallo de validación no repara datos. JSONB no preserva forma textual/JCS: fingerprint se calcula en Go sobre entrada tipada validada antes de almacenar, jamás desde `jsonb::text`.

La clave reglamentaria R-07 contiene exactamente rulesVersion, board, kazans, propietario/localización de ambos tuzdyks y turn. Excluye revisión, ofertas, actividad, IDs y tiempos. Inicial cuenta1; solo movimientos confirmados con salida activa añaden ocurrencias. Un hash igual obliga a comparar la clave completa: si difiere, insertar otra position_id dentro del mismo bucket, sin confundir posiciones. La actualización se serializa por partida. Counts pueden saturarse a3 como caché conservando ocurrencias; hash/count aislados nunca acreditan historia. No truncar ledger para caber en64KiB de AI: limitar/rechazar ese cálculo y aplicar su respaldo autorizado, sin alterar la partida.

### Jerarquía global Game

`PROPUESTA`: READ COMMITTED con locks explícitos y relectura protegida, no aislamiento serializable supuesto. Todas las rutas escritoras adquieren estos niveles en orden; dentro de cada nivel se usa orden total estable:

```text
1. account_guards de TODOS los humanos afectados, UUID ASC
2. rooms por UUID ASC, después games por UUID ASC
3. ratings de TODOS los jugadores afectados, UUID ASC
4. derivados: activity/offers/contributions/aggregates/ledgers/receipts,
   orden fijo por tipo y clave primaria
```

La lista incluye actor y todos los participantes cuyos datos/ratings/ciclo cambien, incluso guardas deleting, origen/destino de vínculo y jugadores de reconstrucción. Tomar cada guarda y rating mediante SELECT individual en orden; no asumir que un `WHERE id IN (...) ORDER BY ...` o un UPDATE múltiple demuestra el orden físico de locks. Guardas ausentes se materializan mediante INSERT controlado en el mismo orden antes de avanzar de nivel y luego se bloquean; `SELECT FOR UPDATE` sin fila no protege una futura inserción. No eliminar guardas para facilitar limpieza mientras exista autoridad/retención pendiente de ese namespace.

Procedimiento: descubrir participantes/recursos sin locks solo como pista → empezar transacción → asegurar/bloquear conjunto de guardas ordenadas → bloquear sala/partida → **releer** participantes, fase, barreras y conjunto afectado. Si aparece una guarda que faltaba o cambia el conjunto de recursos requerido, rollback y reiniciar desde descubrimiento. Está prohibido añadir una guarda menor después de game/rating o continuar con datos previos al lock. Cambios de membresía también toman guardas de miembros existentes y entrante; así join/start y barrera no producen phantoms de participación a espaldas de otra ruta.

Reconstrucción que solo lee contribuciones inmutables de un jugador puede tomar su guarda→rating/aggregate sin game: todo escritor de esas contribuciones toma esa misma guarda antes. Si necesita modificar partidas, descubre y bloquea además sus participantes/juegos en niveles completos. Operación masiva usa manifest/cursor y lotes idempotentes, revalidando conjunto por lote, sin una transacción de red o locks indefinidos.

### Pipeline de un comando oficial

1. Fuera de la transacción deportiva: verificar autenticación/CSRF/S2S del ámbito, forma/versión, límites y admisión de cuota. Calcular fingerprint del intento; no llamar Identity por jugada. Descubrir conjunto de locks.
2. En transacción Game: adquirir jerarquía/releer. Revalidar confianza temporal, permiso de recurso y barrera del actor con tiempo DB fresco después de espera. Actor se deriva del principal, nunca del body.
3. Consultar decisión `(actor,commandId)` antes de stale/turno/fase activa o precondiciones que pudieron cambiar por ese mismo comando. Receipt coincidente y actualmente legible devuelve resultado histórico; otro hash→COMMAND_ID_REUSED. En JoinRoom/JoinRoomByCode un éxito anterior se reconoce antes de volver a exigir código/invitación vigente; el miembro original demuestra permiso actual sobre el resultado. Sin receipt, resolver verificador/cupo/plazo para la nueva admisión. No omitir autorización actual de sujeto/recurso.
4. Si es intención nueva: comprobar fase/deadline y expectedRevision, excepto JoinRoom que controla admisión/cupo bajo lock. En R-07 no exigir turno al reclamante; comprobar posición/historia/umbral/ventana vigente. Verificar movimiento/actor con Go.
5. Ejecutar motor puro con snapshot/contexto bajo `TK-N1-1.0.0`. Completar siembra/efectos y precedencia adoptada. Solo resultado activo añade una aparición candidata. Ofertas/rechazos/cierre administrativo no añaden aparición.
6. Si hay cierre elegible, materializar/bloquear ratings de ambos en UUIDASC, leer valores **actuales**, calcular ambos cambios y siguiente ratingSequence. No usar valores congelados al inicio. Preparar contribuciones/agregados de modalidades permitidas.
7. Persistir juntos: comando/receipt, movimiento si existe, eventos semánticos, snapshot/columnas/revisión, contexto/ocurrencias, lifecycle/outcome y ambos ratings/ledgers/agregados aplicables. Revisión y ordinal se incrementan con overflow comprobado; affectedRows inesperadas abortan. UNIQUE protege una segunda finalización/variación.
8. Commit confirmado → respuesta autoritativa y solo después intento de notificación de05.04. No HTTP, Google, AI, Identity, Ably o espera de usuario dentro de la transacción. Si commit es incierto, no publicar ni afirmar rollback: resolver misma intención según§8.

AI calcula fuera del lock, con grant/callback de07.02; cuando retorna Game abre la operación y revalida base/turno/fase/legalidad. Un movimiento automático AI usa efecto interno deduplicado `(gameId,baseRevision,effectKind)` y fuente Game, distinto de receipt de solicitud pública; no inventa un usuario AI ni acepta callback de AI como comando de movimiento.

## 8. Contratos transaccionales, idempotencia y fallos

### Unidad pgx/sqlc y versiones

`PROPUESTA`: cada servicio construye repositorios propios; una unidad de trabajo recibe pgx.Tx y liga todas las queries al mismo tx mediante `Queries.WithTx`. Ninguna query del bloque usa accidentalmente pool/base fuera de tx. El contexto de Begin no causa auto-rollback en pgx; instalar rollback explícito desde el comienzo, usar contexto acotado de limpieza si el original venció y no devolver una conexión con transacción abierta al pool. Diferenciar error de dominio decidido de error SQL: una decisión que deba guardar receipt retorna resultado de aplicación y permite commit, luego se mapea a HTTP; no se pierde al retornar un error que el helper convertiría en rollback.

Versiones exactas de PostgreSQL/pgx/sqlc/Goose/toolchain, soporte numeric/JSONB y modos de query pooled permanecen `POR_VERIFICAR`. Se consultó documentación PostgreSQL18, sin fijar por ello versión del proveedor. Propuesta de pool inicial por ejecución: maxConns2/minConns0, adquisición/idle/lifetime y timeouts explícitos según presupuesto verificado. Dos conexiones por Function no garantizan cupo global: modelar concurrencia×pool y cuota compartida. Aplicación usa Neon pooled cuando proceda; migración directa, rol DDL independiente. No session advisory locks, estado de sesión persistente, cursor WITH HOLD o tabla temporal como autoridad de partidas/idempotencia. Preparación de statements/protocolo pgx se prueba con pooler, no se presume compatible de una lectura de docs.

### Decisiones e identidad idempotente

Fingerprint `PROPUESTA`, `command-fingerprint/1`: SHA256 de `domain-json/1` JCS sobre objeto versionado con operación,recurso,actorUUID,expectedRevision si aplica y payload completo validado. IDs/versión forman parte; requestId/trazas/hora/cookie de transporte no. Distintos órdenes/escapes JSON equivalentes producen mismo JCS; no normalizar Unicode o redondear números. El actor original y el recurso están ligados aunque el cliente reutilice commandId entre rutas.

El registro común commands también reserva intenciones Game de metadatos admitidas, como RequestAIMove, con su op/fingerprint; ai_requests referencia esa clave y mantiene progreso separado. No permite usar luego esa mismaID en SubmitMove. El receipt de solicitud AI describe proceso/base, no movimiento/appliedRevision nueva, y no avanza gameRevision. ActivityId es un namespace distinto explícito de05.02, con sus propios receipts sin autoridad deportiva.

En creación, el recurso del fingerprint es destino lógico de colección/operación, no un UUID nuevo sorteado en cada retry; el resource_id generado se conserva en receipt. JoinRoomByCode liga su op/ruta y payload exactos; no permite reintentar como JoinRoom bajo la mismaID. Un receipt privado previo puede servir como pista de descubrimiento del recurso para adquirir/revalidar locks y permiso, sin devolverlo antes de autorizar. Si no existe, el índice verificador de código permite descubrir sala/miembros sin locks, seguido por jerarquía y relectura. No se adquiere primero lock del código y después una guarda inferior.

| Clase | Política concreta propuesta |
|---|---|
| Entrada mal formada/versión no soportada, autenticación/CSRF/recurso no autorizado, cuota no admitida | No reservar commandId ni guardar receipt de negocio. Puede haber contador/log seguro separado. Tras corregir una petición que nunca fue admitida el ID no quedó consumido por esa causa |
| Intención nueva válida y autorizada, pero staleRevision, origen ilegal o reclamación sin umbral/oferta incompatible | Decisión de negocio persistida bajo locks: commands+receipt con decision=rejected, fingerprint, status/Problem seguros, decisionRevision/decidedAt; sin movimiento/revisión/aparición/Elo. Repetir mismo hash devuelve ese rechazo; para decidir otra intención tras reconsulta se usa nuevoID |
| Intención aceptada | commands+receipt accepted y todos los efectos en el mismo commit. Receipt histórico con appliedRevision, resultado y versiones; no se presenta como estado vigente |
| Misma clave existente, otro hash |409 COMMAND_ID_REUSED sin reemplazar receipt ni ejecutar de nuevo; no se crea una segunda decisión en esa clave |
| Fallo SQL/timeout con rollback confirmado | Ningún receipt/efecto de esa transacción; misma intención puede reintentarse. Una cuota admitida antes puede haberse consumido independientemente y no se cuenta como jugada |
| Commit/resultado de conexión desconocido | Estado UNKNOWN; conservar misma clave/hash. Consultar/reintentar idempotentemente, adquirir mismos locks y leer receipt. Ausencia momentánea no demuestra rollback ni permite usar otroID |

La autorización actual previa al receipt comprueba identidad original, lectura de recurso y barrera; no exige de nuevo que el actor tenga turno si perdió turno por su éxito previo. Las precondiciones para **nuevo efecto** se evalúan después de no encontrar receipt. U vinculado no lee receipt G, aunque vea historial terminado. Rechazos transitorios por datos/historia incompletos o dependencia indisponible no se congelan como decisión reglamentaria: no reservan ID; recuperar datos y reintentar misma intención mantiene las reglas.

Purga propuesta: separar payload privado del índice de deduplicación. Cuando política permita purgar el primero, conservar tombstone mínimo con actor/recurso/commandId/fingerprintVersion/digest/decision y marca de resultado no disponible; no volver a ejecutar. Mismo hash devuelve estado de decisión purgada sin exponer contenido, otro hash409. Ese mínimo es pseudónimo; plazo/campos dependen de política07.03/RISK-10. Si la política exige retirar incluso ese mínimo, cerrar previamente el namespace/recurso para rechazar todos sus comandos antiguos; no borrar la única protección y seguir aceptando IDs como nuevos. No se fija retención jurídica indefinida por conveniencia técnica.

### Expiración, actividad y efectos internos

Después de locks se obtiene tiempo DB fresco, propuesta `clock_timestamp()`; no un timestamp del cliente, ni `now()` de inicio de una transacción que esperó. Solo en phase=active se aplica recuperación24h: para cada participante humano, deadline=lastActivityAt+24h; vence min(deadlines). Si `tDB>=expiresAt`, una rama de cierre **interno** idempotente persiste recovery_expired/inconclusive una vez antes de permitir actividad, sin Elo. Pending usa su plazo30min y un terminal previo nunca se sustituye por recovery_expired al leerlo más tarde. Esa rama no ejecuta el comando de usuario: confirma archivo/registro interno y luego devuelve410; no guardar un rechazo de negocio afirmando que cambió por sí solo el tablero. Si falla ese commit, no declarar archivo confirmado. Duplicate previo puede recuperar su receipt histórico autorizado, sin renovar actividad.

Solo una actividad nueva válida del propio participante, ResumeGame o HeartbeatGame renueva su fila tras comprobar token/margen recuperable de07.01/07.02. GET/Ably/rival/duplicado no. activityId tiene fingerprint y resultado fijo; dos pestañas con el mismoID no extienden dos veces. Nuevos IDs requieren admisión y reloj de servidor. Heartbeat/resume incrementan activityVersion únicamente, no gameRevision/moveOrdinal/repetición. La expiración oportunista de una consulta no cuenta como actividad; una lectura puede observar expiry lógico antes de materialización. Estado completo sigue no-store/sin304 por revisión de05.02.

Precisión06.03 de confianza temporal: bajo locks comparar tDB con el máximo lastActivityAt persistido de ambos participantes. Si tDB retrocedió por debajo de ese máximo, rechazar nueva renovación/transición dependiente de reloj con DATA_UNAVAILABLE503/diagnóstico seguro, sin reducir timestamps, fingir pausa o fabricar resultado. No se rechaza por ese motivo la consulta de un receipt histórico actualmente autorizado; su decisión no renueva y proyección describe estado actual. Verificación del reloj/operación real permanece POR_VERIFICAR.

Pending room usa política distinta de30min de inactividad de06.01; no transforma ese plazo en reloj de partida. Expiry/renovación, limpieza y comandos toman las mismas guardas. Limpiar tarde no concede validez ni cambia inconclusa a derrota.

### Ratings, contribuciones y reconstrucción

Final de G1(A,B) y G2(A,C): ambos necesitan guardaA; uno espera antes de game/rating. El primero confirma usando ratingA actual; el segundo, tras adquirir guardas/ratings, relee el nuevo valor y aplica su resultado. Los pares completos se bloquean ordenados, no cada rating según color o ganador. `ratingSequence=prev+1` por jugador bajo lock y ledger único reflejan su orden de efectos; una secuencia SQL global no demuestra orden de commits.

Resultado/outcome, dos ratings/ledgers y contribuciones/agregados elegibles se confirman o revierten juntos. Inconclusa no modifica Elo/provisionales y conserva causa separada; estadísticas generales usan inclusión por modalidad/política de07.04. Recalcular agregado toma guarda del jugador, lee contribuciones canónicas completas de esa política y reemplaza agregado/versión en una transacción. Todos sus escritores toman esa guarda; no mezclar SUM viejo con incrementos nuevos. Recalcular rating se verifica desde ledger/sequence y política original, no modifica históricos automáticamente ni usa orden de timestamps/global sequence como sustituto. Reparación de rating exige plan/autorización aparte.

### Vínculo, barrera y limpieza recuperables

Vínculo G→U conserva UUID originales y rankedAtStart. Identity prueba la relación por S2S; Game bloquea G/U y registra operationId/hash, cutoff DB y manifest de partidas terminadas autorizadas. El conjunto queda congelado en primera aplicación, antes de procesar lotes; reintentos no incorporan partidas que terminaron después. Cada lote toma guardas y juegos ordenados y registra progreso/items únicos. Solo al verificar todo el manifest se informa applied; historial activo y receipt G no pasan a U. No hay HTTP dentro de la transacción ni atomicidad entre bases.

`RequestDataCleanup/1` de05.02 liga path operationId+step y body mediante S2S/JCS. El paso **barrier** con scope block_actor no necesita policyVersion: bajo guarda del titular fija deleting/blocked, impide acciones/altas/inicios del titular y devuelve `ACK_REVOKED` persistido. Ese acuse no significa supresión completa. Raíz operationId/subject y hash de cada paso son inmutables.

Deleting **no** bloquea la guarda como si todo efecto estuviera prohibido: rival autorizado puede mover/renunciar/reclamar y Game puede aplicar finales internos y ambos efectos Elo/ledgers sobre miembros elegibles. No cambia membership/rankedAtStart, no adjudica forfeit/account_deleted ni archiva por borrar. Si queda esperando, solo vencimiento24h real produce recovery_expired. Barrera no borra datos existentes; por ello esos efectos siguen íntegros mientras falta política de limpieza.

El paso **cleanup** exige barrera confirmada y policyVersion aprobada, inmutable y verificable en configuración/registro autorizado. Sin política devuelve proceso `BLOCKED_PENDING_DATA_POLICY`, no ACK_CLEANUP_COMPLETE ni policyVersion=null aceptada. La política debe indicar mínimos para partidas rivales, guardas/ratings/ledgers/receipts/backups y conservación pseudónima. Se procesa por manifest/cursor bajo la misma jerarquía, sin borrar guardas necesarias, recrear perfil o suprimir efectos de otro jugador. `ACK_CLEANUP_COMPLETE` solo tras verificación de todo el alcance aprobado; Identity finaliza después de comprobarlo. Cambiar sujeto/alcance/política de un paso existente es conflicto; otra política requiere transición autorizada, no reusar clave. No se afirma anonimización por ocultar alias.

### Cuotas y grants AI

Contadores por ventana de07.02 se actualizan atómicamente en transacción corta del dueño, con claves ordenadas y admisión solo si todos caben. Cuota transaccionalmente separada del comando puede contar un intento rechazado/rollback; no implica movimiento confirmado ni se reembolsa por suposición. Antes de emitir grantAI Game verifica principal/recurso/base, bajo guardas y lock breve, reserva límite de pendientes y persiste request/grant; commit y liberar locks **antes** de HTTP AI.

ConsumeAIGrant verifica S2S/hash/budgets/attemptId interno/deadline y realiza CAS issued→claimed en Game. Claim/receipt son una decisión fija; mismo handler/intento recupera el mismo acuse vigente, otro intento rechaza. Tomar guardas del sujeto y recurso si se revalida partida antes de grant-row; nunca volver desde grant hacia game. Crash/timeout trasclaim puede consumir sin resultado, y estado incierto no autoriza cómputo. Completed libera reserva de pendientes sin reabrir grant; expire lógico funciona sin cron frecuente. AI no tiene DB, no guarda autoridad global en RAM ni llama una ruta para mover/Elo. Sin exactamente una vez de cómputo o entrega.

### Reintentos SQL y resultado desconocido

Propuesta: máximo3 intentos **de transacción completa** para SQLSTATE40001/40P01, con backoff acotado25/75ms más jitter y siempre dentro del deadline de petición. Releer datos y recalcular motor/ratings en cada intento; no repetir solo el último UPDATE. Deadlocks siguen siendo posibles por defectos/otras dependencias, no se declara ausencia probada. Cambiar el set de guardas implica rollback/reinicio explícito con límite3 igualmente, sin ampliar alcance.

Otros errores no se reintentan automáticamente: UNIQUE esperado se traduce al conflicto de dominio/consulta del receipt después de rollback cuando corresponda; constraint/invariante inesperada bloquea y se investiga; cancelación/lock timeout retorna fallo seguro según certeza de rollback. Commit con error de conexión no es40001/40P01 conocido: clasificar UNKNOWN y resolver por clave, sin emitir nuevo comando, publicar o recalcular como si hubiera fallado. Rollback explícito se intenta incluso con contexto original cancelado; fallo de limpieza exige descartar conexión, no devolverla como sana al pool.

## 10. Justificación y alternativas

READ COMMITTED más guardas/relectura hace explícitas las secciones críticas y evita atribuir serialización global al aislamiento por defecto. Añade contención por jugador, aceptada aquí como propuesta de integridad que debe medirse. Solo lock de partida no protege rating compartido ni barrera frente a otra partida. Serializable es alternativa revisable con sus reintentos, sin reemplazar automáticamente esta disciplina.

Snapshot JSONB compacto agiliza estado y conserva formato; movimientos/contexto/contribuciones relacionales permiten consultas/replay/verificación. Go sigue siendo dueño de validación profunda; ni JSONB ni CHECK locales acreditan una secuencia alcanzable. numeric20 evita limitar silenciosamente uint64 a bigint firmado, con coste de mapping/índice pendiente de medir.

Receipt y digest separados permiten minimizar contenido sin recrear una intención antigua. Rechazos de negocio persistidos estabilizan reintentos; inválidos/no autorizados no reservan IDs ajenos. Guardas/tombstones retienen relaciones pseudónimas bajo política, no prometen anonimización. Redis/cola/outbox, cuarto servicio o SQL cruzado no son alternativas obligatorias ni están autorizados; una propuesta que cambie arquitectura/coste requiere aprobación.

## 11. Ejemplo técnico explicado

Fragmento SQL **PROPUESTA** solo dentro de Markdown, no migración creada/ejecutada. Ilustra el rango, clave idempotente y una protección adicional; no representa el esquema completo ni prueba invariantes entre filas.

```sql
CREATE TABLE game.account_guards (
  subject_id uuid PRIMARY KEY,
  status text NOT NULL CHECK (status IN ('active','blocked','deleting','tombstone'))
);
CREATE TABLE game.commands (
  actor_uuid uuid NOT NULL REFERENCES game.account_guards(subject_id),
  command_id uuid NOT NULL,
  resource_id uuid NOT NULL,
  fingerprint_version integer NOT NULL CHECK (fingerprint_version = 1),
  fingerprint bytea NOT NULL CHECK (octet_length(fingerprint) = 32),
  decision text NOT NULL CHECK (decision IN ('accepted','rejected')),
  receipt_state text NOT NULL CHECK (receipt_state IN ('available','purged')),
  decision_revision numeric(20,0) CHECK
    (decision_revision BETWEEN 0 AND 18446744073709551615),
  PRIMARY KEY (actor_uuid, command_id)
);
```

El schema `game` del ejemplo se presupone creado dentro de Game DB; es un fragmento, sin acceso a Identity. `receipt_state=purged` no borra la decisión accepted/rejected ni el fingerprint. Orden de ejecución ilustrativo, sin valores de rating inventados ni locks de red:

```text
G1(A,B) y G2(A,C) online terminan en paralelo; supóngase UUID A<B<C.
T1: guardaA -> guardaB -> roomR1 -> gameG1 -> ratingA -> ratingB
T2: espera guardaA ANTES de gameG2
T1: lee A0/B0 -> outcomeG1 + A1/B1 + ledger + agregados + receipt -> COMMIT
T2: guardaA -> guardaC -> roomR2 -> gameG2 -> ratingA -> ratingC
T2: lee A1/C0 -> outcomeG2 + A2/C1 + ledger + agregados + receipt -> COMMIT
Si falla cualquier efecto T1: ROLLBACK; T2 leerá rating confirmado real.
No usar A0 guardado al iniciar G2 ni SQLsequence global como orden de commit.
```

La fila de guardaA serializa ambos finales. Si descubrimiento de G1 omitió un participante añadido antes del lock, T1 revierte/reinicia en vez de añadir esa guarda tarde. Tras commit, repetir mismo commandId/hash devuelve receipt previo antes de stale; cambiar expectedRevision con ese mismoID es otra carga y409. El ejemplo no ejecuta motor, Elo o PostgreSQL.

## 12. Casos límite, fallos y seguridad

| Caso | Resultado exigido / recuperación |
|---|---|
| Dos jugadas de misma revisión, distinta intención | Una acepta; la otra decide stale/terminal sobre estado revalidado, sin segundo movimiento |
| Misma intención en dos conexiones | Guarda actor y UNIQUE producen un receipt; respuesta equivalente autorizada, sin doble aparición/final/Elo |
| commandId con otro recurso/body |409 sin reemplazar fingerprint/decisión existente |
| Fallo entre snapshot, movimiento, outcome, rating o agregado | Rollback completo; sin estado parcial ni notificación oficial |
| Commit incierto o respuesta perdida | UNKNOWN/misma intención y consulta receipt; no suponer rollback o emitir segundo comando |
| Finales de distintas partidas con jugador compartido | Guardas y ratings ordenados; segundo lee valor nuevo, ambos ledgers/contribuciones completos |
| Guarda/rating/familia inexistentes | Materializar/proteger bajo nivel anterior y UNIQUE; SELECT vacío no es lock de ausencia |
| Miembros cambiaron antes de lock | Releer y reiniciar set; no adquirir guarda inferior después de game |
| Reclamación versus movimiento/terminal | Primera operación válida sobre revisión prevalece; ambos participantes pueden reclamar sin turno; terminal definitivo no abre ventana |
| Heartbeat/reanudación versus expiry/limpieza | Tiempo fresco tras lock y archivo antes de renovar en igualdad; duplicado/GET/rival no prolonga propio |
| Link/cleanup interrumpido/repetido | Raíz/paso/manifest/hash fijos; reanudar con acuses, no efecto doble ni SQL cruzado |
| Borrado y rival legal | Actor deleting bloqueado; rival/sistema conservan permisos, elegibilidad y efectos; sin outcome por cuenta borrada |
| Callback grant repetido/distinto o DB caída | Mismo intento recupera acuse vigente; otro rechaza, incierto no calcula, AI sin DB |
| JSONB/regla/contexto corruptos | Error técnico y preservación; no normalizar piedras, improvisar ganador o declarar norma pendiente |
| Purga de receipt/conexión cancelada | Tombstone impide reuso; rollback/descartar conexión evita transacción abandonada |

Roles de aplicación no tienen DDL, permisos ajenos o credenciales migradoras. Secretos SQL/DSN/PII/cookies no se imprimen en errores, ejemplos o trazas. UUID/IDs de juego/ledger siguen sujetos a política de datos. Local/práctica no insertan comandos deportivos ni contribuciones confiables; tener un estado162 no lo hace oficial.

## 15. Observabilidad, migración y recuperación

Propuesta de evidencia: requestId/traceId, comando/operación/paso, servicio/build/esquema/reglas, revisión antes/después, cantidad de locks/restarts, SQLSTATE seguro, estado BEGIN/commit/rollback/UNKNOWN, receipt/replay y duración observada. Métricas de pool/espera/aborts/grants/procesos pendientes y reconstrucción sin payload privado, SQL con parámetros sensibles, DSN, cookies, secretos o exportaciones. IDs técnicos son pseudónimos sujetos a política de datos.

Migración/limpieza conserva fuentes de verdad y checkpoints/versiones. Backfill se deduplica por job/cursor/clave, participa en guardas y valida antes/después; nunca descarta ledger para cumplir cuota. Un rollback de servicio no deshace commits, vuelve vigente un refresh, libera grant consumido o restaura PII borrada. Restauración requiere plan/ensayo autorizado de [10.03](../../index.md#spec-10-03)/[10.04](../../index.md#spec-10-04), `PENDIENTE_LOTE_5`; no hay RPO/RTO acreditados.

Sin outbox duradero obligatorio: semantic_events es historia oficial, no un proceso persistente que garantice reintentar publicación. Un crash posterior al commit puede perder aviso; REST/receipt recuperan estado confirmado. Añadir outbox/cola/Redis cambia operación y requiere propuesta/aprobación separada.
