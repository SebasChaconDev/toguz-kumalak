## 2. Objetivo, alcance y valor

Mantener una réplica visual del estado confirmado por Game aunque un aviso se pierda, llegue repetido o aparezca después de otro más reciente. El participante debe distinguir selección, intención pendiente, movimiento confirmado y recuperación, sin que el navegador decida reglas o convierta una interrupción en un resultado.

Incluye suscripción privada, confirmación visual, reconciliador, foco/red/pestañas, degradación REST, presupuesto compartido y contratos consumidores de presentación. Conserva MVP base y ampliado, incluyendo vista HTML equivalente a 3 D. No implementa un motor cliente, socket propio persistente, presencia deportiva, proveedor alternativo o infraestructura adicional.

El permiso de [AGENTS](../../../AGENTS.md)/[PLANS](../../../PLANS.md#lote-3) es documental. No se crean código, schemas ejecutables, clientes SDK o recursos; no se emiten tokens, conectan proveedores, ejecutan pruebas de producto o acredita gratuidad por leer documentación.

## 5. Invariantes y entidades

- Game/PostgreSQL confirmado es verdad oficial. Ably solo anuncia disponibilidad de revisión; ack, conexión o timestamp del proveedor no adjudican movimiento, turno, resultado o Elo.
- Un aviso lógico confirmado puede llegar cero, una o muchas veces. Publicar después de commit conserva la ventana de aviso perdido; no hay entrega exactamente una vez o ACID PostgreSQL/Ably.
- La réplica oficial solo adopta snapshot autorizado o respuesta confirmada de Game. Notice no contiene tablero y su llegada no habilita aplicar un delta inventado.
- gameRevision uint64 decimal es monotónica por agregado. `activityVersion` por participante y `rematchVersion` por intent son independientes; misma gameRevision puede contener metadatos más recientes.
- Solo phase=active y allowedActions actuales permiten una intención deportiva; pending con candidato inicial no es jugable, expired no inicia y terminal no se reabre.
- Selección/hover son locales; comando pendiente no anima ejecución definitiva ni se retransmite con otra commandId para resolver incertidumbre.
- Ningún aviso/GET/polling/attach/rewind renueva actividad, sesión, sala o revancha. No se infiere derrota o expiración oficial por detectar una desconexión del transporte.
- Cada pestaña conserva su autorización. Compartir una señal de revisión no transmite identidad, tokens o permiso de controlar otro participante.

Entidades técnicas **PROPUESTA**: ConfirmedReplica, SyncStatus, ReconcileTarget, ContextEpoch, PendingIntent, ActivityMetadata y AnimationBatch. Son estado de cliente sin autoridad de juego; las credenciales permanecen en memoria/cookies conforme a sus dueños, nunca localStorage.

## 7. Diseño de suscripción, reconciliación y consumo

### Canal y fronteras de confianza

Game confirma PostgreSQL y después ejecuta el intento de publicación de 05.04. Su presupuesto propuesto de 750 ms pertenece exclusivamente al adapter Game, incluyendo retries del SDK y tiempo restante del request; no es timeout del navegador o SLO de entrega. Un fallo conserva el commit; no promete reintento durable ni devuelve otra jugada. No se exige outbox, cola, Redis o socket propio.

Un canal por agregado: `env:game:<gameUUID>`, con env configurado/aislado y UUID autorizado. `IssueAblyCapability/1` POST `/api/v1/games/{gameId}/ably-capabilities` recibe `{}`; Game deriva canal/clientId desde principal/recurso. Capacidad **message-subscribe exacta**, sin wildcard/publish/presence/history/object/annotation ni herencia por omitir capability. Ni admin ajeno, invitación o vínculo de historial acreditan participación activa. Sin presencia Ably como árbitro de sala, conectividad del rival o resultado.

TTL nominal 300 s y expiración estricta de 07.02/05.04: mínimo de tGameDB+300 s, exp del acceso, horizonte firmado y permiso temporal del recurso. Sin leeway del JWT para Ably; pending limitado por sala y active por recuperación; terminal no recibe capacidades nuevas. Token Ably en memoria del SDK, no URL/localStorage/log/BroadcastChannel. Refresh de producto conserva su flujo separado; no presentar token Google/Ably al API Game.

Propuesta de renovación: programar una sola autorización anticipada cuando falten hasta 30 s de capacidad, con jitter entre 0 y 5 s, siempre antes de exp y sin reiniciar su plazo. Si su vida restante inicial es <=30 s, renovar primero el acceso del producto y pedir capacidad solo después; máximo dos llamadas de capacidad por ciclo y cuotas 07.02 (12/min por sujeto+partida, 30/min por sujeto). El callback de autenticación SDK comparte ese mismo single-flight y presupuesto, sin otro loop paralelo. Fallo/401 no origina renovación infinita: detener suscripción, reconciliar REST cuando la identidad lo permita y mostrar acción segura. Si la release solo admite subscribe genérico, informar incompatibilidad y usar REST; no ampliar permisos para hacer funcionar el SDK.

Una capacidad anterior puede recibir hasta exp avisos mínimos después de terminal/logout/barrera y mensajes recientes por rewind incluso sin history. No se configura rewind de aplicación en este perfil, pero su ausencia de permiso history no constituye exclusión criptográfica de lo reciente. REST reautoriza detalle; residual y datos mínimos siguen 05.04/07.03. No se promete revocación instantánea ni se guarda recoveryKey sensible para sostener 24 h.

### Entrada y restauración de una réplica

```mermaid
sequenceDiagram
    participant C as Cliente
    participant G as Game REST
    participant A as Ably
    C->>G: Capacidad del game autorizado
    G-->>C: Canal y capacidad exactos
    C->>A: Listener + attach
    A-->>C: Notice posible → conservar objetivo mayor
    C->>G: GET snapshot no-store
    G-->>C: Phase, revisión, estado y metadatos
    C->>C: Instalar confirmado; comparar objetivo pendiente
    C->>G: Otra lectura acotada solo si aún falta revisión
```

Cambiar gameId, principal/familia de sesión o abandonar la pantalla incrementa ContextEpoch, desregistra listeners y cancela solicitudes cuando sea posible. Una respuesta de epoch anterior se descarta aunque abort no haya detenido la red. Nunca instalar estado de otra partida/identidad por terminar tarde.

Instalar listener **antes de attach** y attach antes del GET inicial cuando el transporte esté disponible. Mientras se obtiene snapshot mantener solo la mayor revisión de avisos validados, no una cola sin límite de mensajes. Propuesta: hasta 5 s para establecer attach; si falla o vence, iniciar REST sin esperar Ably indefinidamente, marcar transporte degradado y conservar las reglas de nuevo attach al recuperar. Es deadline local candidato, no garantía de timers o red. En terminal, ir directamente a REST sin nueva capacidad.

El GET usa ReadRoom para controles pending o ReadGame para estado oficial; ambos se coordinan por gameId y revisión común. Una pantalla no consulta ambos periódicamente para obtener lo mismo. InvitationGrant se extrae del adjunto privado del creador a memoria temporal autorizada, nunca se copia al estado público, caché de avisos o telemetría. No necesita otro canal Ably. Si GameView.phase pasa a expired/terminal, detener acciones y consultas propias de una partida active aunque exista un Notice antiguo room.updated.

### Algoritmo propuesto del reconciliador

1. Validar nombre `game.notice.v1`, canal/gameId esperado, NoticeV1 cerrado y versiones/rango/ID de 05.04. Revisiones son strings canónicas 0..18446744073709551615; comparar con BigInt o longitud/orden decimal, nunca Number/parseInt/operaciones float. NoticeID es `g:<gameUUID>:r:<revision>`, distinto de UUID semántico y serial Ably.
2. Mantener highestTarget=max(revisiones válidas recibidas, objetivo ya pendiente). Aviso igual/menor puede descartarse como disparador de estado; no descartar eventos semánticos distintos por compartir revisión. Aviso malformado/incompatible marca necesidad de snapshot autorizado, sin copiarlo como tablero ni aceptar otro rulesVersion por default.
3. Un solo fetch de estado en vuelo por gameId/pestaña, compartido por entrada, aviso, foco, reconexión, sondeo y acción manual. Coalescer disparadores durante 250 ms cuando no exista fetch; si llega otro mayor durante el fetch, conservarlo. Toda lectura y retry consumen los límites de la tabla siguiente.
4. Verificar snapshot/phase/versiones y permiso actual. Si su revisión es mayor, reemplazar réplica oficial; si es menor, no instalar posición ni metadatos. Si igual, conservar posición confirmada y procesar metadatos independientes. Snapshot igual con posición/terminal distintos es divergencia de datos, no desempate por llegada: bloquear acciones, diagnóstico seguro y reconsulta acotada; si persiste, error visible sin inventar reparación.
5. **Propuesta de precisión de RecoveryView:** identificar cada participante por subjectId UUID y exigir su activityVersion decimal uint64, consumiendo el contador que 05.03 ya incrementa. Actualizar lastActivityAt/deadline solo con versión mayor; igual debe tener iguales metadatos o disparar divergencia. Aplicar este merge incluso si la posición acaba de avanzar: una respuesta con revisión deportiva mayor no reduce una versión de actividad ya conocida. No mezclar deadline de una versión con timestamp de otra. Un heartbeat HTTP tardío no reduce un deadline nuevo. Campo ausente no recibe versión 0 por default: informar incompatibilidad de metadatos antes de reanudar. Recuperación de 24 h solo corresponde a phase active; en terminal puede mostrarse su registro final/descriptivo, sin renovar o mantener timers de actividad. Pending/expired usan la proyección temporal de sala, sin inventar RecoveryView active.
6. RematchVersion se compara únicamente dentro del mismo rematchId. Proyección rematch actual procede del GET terminal single-flight de su epoch, no de receipts históricos. Un intent nuevo puede comenzar versión 0: se adopta como otra entidad desde esa lectura serializada, sin comparar su 0 con el 1 de un intent previo. Tras enviar/confirmar una intención local invalidar la lectura de metadatos iniciada antes y programar otra; receipt solo resuelve su propia decisión/IDs. serverTime informa al usuario, no ordena revisiones ni sustituye versiones ante relojes ajustados.
7. Si snapshotRevision>=highestTarget, cerrar ciclo y mostrar recuperado; si falta, como máximo dos lecturas adicionales dentro del ciclo/presupuesto. Si siguen faltando datos, conservar el mayor objetivo, estado sincronizando y diferir al próximo disparador admitido; no bucle inmediato. Un aviso superior puede preceder a una lectura atrasada o permanecer sin resolver por fallo; no fabricar revisiones intermedias.
8. Solo habilitar nueva intención cuando exista snapshot compatible, phase/allowedActions apropiados y ninguna intención propia incierta o reconciliación requerida pendiente. Una carrera posterior puede devolver 409 y obliga reconsulta, no aplicación local. En REST degradado, completar lectura autorizada antes de permitir actuar; un estado confirmado no reserva turno ni impide cambios posteriores del rival.

Metadatos terminales/actividad se reciben con `Cache-Control:no-store`, sin 304/ETag condicionado solo a gameRevision. La monotonicidad se conserva también al instalar GameView de una respuesta de comando: puede aportar posición más nueva; receipt histórico resuelve la intención pero no reemplaza una revisión posterior. Para metadatos usar sus versiones/epoch y programar GET actual si la respuesta no aporta evidencia suficiente. Un retry reconocido no extiende plazos.

### Selección, confirmación y semántica visual

El cliente puede resaltar un pozo inmediatamente y pedir legales/preview Go según 05.02. Guardar PendingIntent con commandId/revisión/origen y enviar a Game. Mostrar «confirmando» y bloquear otra ejecución propia hasta resolver esa intención. No mover piedras definitivas, cambiar turno/kazanes o declarar ganador desde preview, click o Notice.

Respuesta confirmada autorizada o ReadCommandResult del mismo actor demuestra la decisión histórica; si HTTP se perdió, repetir exactamente la misma intención o consultar recibo. No crear otra commandId por timeout, ni tomar una ausencia temporal de recibo como rollback. Campo effect=unknown mantiene incertidumbre hasta resolver o mostrar indisponibilidad. Una resolución accepted puede ser antigua respecto al snapshot actual: informa «movimiento confirmado» sin retroceder tablero.

Para animar una transición, reunir desde respuesta Game o ReadReplay **todo su rango semántico** compatible, con historia/ordinales y sequence contigua de 05.04. Una revisión puede abarcar movimiento y cierre en entradas distintas; reunir sus eventos sin duplicarlos entre registros/páginas. Deduplicar por eventId y clave(gameId, revision, sequence); mismo identificador con payload distinto es divergencia. No sumar una aparición/Elo al leer o animar.

Solo si se conoce la base confirmada y lote completo se permite animación definitiva hacia el snapshot confirmado; en cualquier frame la réplica oficial ya corresponde a ese resultado. Si faltan páginas, excede presupuesto o llegó otro estado, omitir/cancelar animación y dibujar el snapshot actual con último movimiento confirmado. No reconstruir deltas con history/rewind Ably o motor TypeScript. HTML/3 D consumen los mismos refs/datos, permiten omitir animación y anuncian estado/captura/tuz/resultado de forma accesible. Disponibilidad de animación no condiciona continuar una partida con snapshot íntegro.

### Estados visibles y degradación

| Estado visible | Condición y acciones |
|---|---|
| conectado | Transporte adjunto y snapshot compatible reconciliado, sin objetivo mayor pendiente. Permisos/phase siguen Game, no conexión |
| sincronizando | Entrada, foco, hueco, formato desconocido o lectura/reintento pendiente; conservar último tablero marcado pendiente y bloquear nueva ejecución |
| desconectado | No puede obtenerse confirmación REST o identidad verificable; mostrar última revisión como histórica, sin aceptar nuevos movimientos offline |
| recuperado | Snapshot actual instalado tras interrupción; anunciar último movimiento/phase. Puede indicar «notificaciones interrumpidas; actualizado por REST» |

`connected` SDK no equivale por sí solo a conectado del producto. Un corte solo Ably puede terminar en recuperado por REST y permitir comandos autorizados, indicando degradación; caída Game/PostgreSQL impide confirmar aunque el socket siga conectado. Identity caído conserva únicamente acceso/material válidos 07.02 y luego requiere renovar, sin consulta Identity por jugada ni bypass. Un estado de interfaz nunca adjudica renuncia/inconclusa.

### Cadencias, backoff y límites propuestos

Un scheduler de pestaña reúne disparadores; no un timer por listener o por componente. Tabla de **PROPUESTA sync-policy/1**, contadores de cliente sobre tiempo monotónico transcurrido y ventanas móviles; no sustituyen límites server-side:

| Actividad | Cadencia / techo inicial |
|---|---|
| Avisos/foco/red/manualmente actualizar | Coalescing 250 ms y single-flight; repetir foco/online dentro de 2 s se agrupa; siempre sujeto a caps |
| Comprobación silenciosa pending/active con Ably sano | Cada 60 s con jitter±20%; detecta último aviso perdido incluso sin hueco posterior |
| Fallback REST con solo Ably caído | Cada 5 s con jitter±20% mientras visible, hasta 10 min por episodio; después parar sondeo automático y mostrar actualización manual/intent de reconectar. No cerrar partida |
| Lectura fallida por error transitorio | Ciclo máximo 3 intentos totales: inicial +2 retries; esperas con jitter uniforme entre 0 y 1 s y 0 y 3 s, deadline local total 15 s. Respetar Retry-After si mayor y cabe; si no, diferir fuera del ciclo |
| Presupuesto de lecturas REST de pestaña | Máximo 30/min móvil y 120/10 min móvil entre todas sus partidas. TODO GET de API de producto iniciado por esta pantalla cuenta: estado, legales, ReadAIRequest, perfiles/sesión/historial, retry, replay, recibos y poll terminal; también POST de solo lectura como batch público. No permitir un loop de ayudas fuera del scheduler. Al agotarse deferir/informar, sin manual que eluda cap |
| Replay para una animación | Máximo 10 páginas por ciclo visual y 5 s de trabajo de red programado, dentro del cap general. Si falta rango, snapshot sin animación; no truncar historia persistida |
| Rematch terminal | Consumir 06.01: inmediata y cada 15 s, máximo 40 lecturas/10 min visible, dentro del cap general; ninguna nueva capacidad/Notice del predecessor |
| Pantalla oculta | Suspender comprobaciones/poll terminal/fallback; cerrar/detach Ably tras gracia propuesta 30 s si aún oculta, sin prometer puntualidad de timers del browser. No iniciar heartbeat por recibir avisos; 06.03 define actividad explícita |
| Reentrada visible | Incrementar epoch de sincronización, reautorizar/attach si aplica y GET aun cuando SDK diga resumed; no reproducir una cola ilimitada de animaciones antiguas |

Fallback 10 min es presupuesto del cliente, no ventana recuperable ni fin de partida. Al detener automatismos, una acción manual puede iniciar una lectura/ciclo admitidos y una tentativa de reconectar; no reinicia los contadores móviles ni repite automáticamente episodios de 10 min sin acción nueva del usuario. Comprobación sana periódica es limitada por minuto/ventana y solo mientras la pantalla está activa, sin sondeo global permanente de partidas no abiertas.

POST de autenticación/refresh/capacidades, comandos y actividad no se disfrazan de lecturas de ese cap: conservan sus cuotas/single-flight y límites de07.02/06.03, y se suman al presupuesto conjunto REST de infraestructura de abajo. Los GET/POST de solo lectura realizados por componentes auxiliares de esta pantalla sí comparten el cap, aunque su dueño sea Identity o Game. Assets estáticos y tráfico interno de servicios se contabilizan en su presupuesto de infraestructura, sin atribuirlos al reconciliador del navegador.

429 respeta Retry-After, sin nuevo ID/intención ni loop de renovación.401 dirige al flujo single-flight de identidad una vez; después requiere acción/servicio disponible.403/404 denegados, 410 expired, contrato incompatible o phase terminal cancelan los automatismos que ya no procedan.5 xx/timeouts admiten retries de lectura acotados; mutaciones conservan su identidad y siguen 05.03. Abort de lectura no prueba rollback de un POST concurrente.

Reconexión Ably usa **un solo dueño de retries**. Se permite al SDK recuperar brevemente dentro de un episodio propuesto de 120 s; la aplicación no superpone otro loop connect. Al siguiente turno disponible tras agotar ese episodio, cerrar la conexión para detener retries y continuar REST limitado. Instanciar/reabrir requiere disparador explícito (retorno visible, red recuperada o acción del usuario), máximo 3 aperturas de aplicación por minuto/pestaña con jitter 0–3 s. SDK puede ejecutar varios intentos internos; medir/configurar su techo efectivo y no afirmar 3 intentos de transporte. Estado failed por autorización no se reintenta como fallo de red. La suspensión de timers en segundo plano reduce precisión; límites de SDK/servidor y medición siguen pendientes.

Cada pestaña puede abrir una conexión y el canal de su partida visible; varias pestañas multiplican consumo. Web Locks/BroadcastChannel pueden elegir observador local para reducir lecturas/conexiones, como optimización propuesta sin autoridad de identidad: solo hints no sensibles de revisión/estado, nunca tokens o comandos firmados. Sin ese soporte, cada pestaña cumple sus caps y Game reautoriza; ninguna garantía de cuota global depende de coordinación local. El cálculo presupuestario incluye pestañas independientes.

## 8. Contratos, tipos, errores y versiones

No añadir esquemas alternativos. Consumir **NoticeV1 y SemanticEventV1 de 05.04**: siete tipos del motor MoveStarted, StoneSown, TuzdykReceived, StonesCaptured, TuzdykCreated, TurnChanged, GameEnded y cinco de aplicación RoomCreated, RoomUpdated, GameStarted, DrawOffered, DrawRejected. ## 10. Justificación y alternativas

Attach antes de GET y maxTarget cierran la carrera de entrada sin exigir guardar todos los avisos. REST single-flight y caps evitan una lectura por cada mensaje duplicado; la consecuencia es demora visible bajo presión, que debe medirse. Revisión decimal evita pérdida de precisión JavaScript y sus versiones separadas permiten renovar actividad/revancha sin simular otro movimiento.

Confirmar antes de animar evita mostrar como oficial una jugada rechazada. Exigir lote completo solo para la animación permite recuperar por snapshot aunque falte historia visual; introducir reglas o completar piedras en el navegador cambiaría la autoridad aprobada. No se exige recibir todas las animaciones antiguas para estar al día.

Fallback REST mantiene comandos confirmables cuando falla solo Ably, pero consume invocaciones/DB y puede agotarse; límites y estado visible hacen explícita esa compensación. Las reservas de planificación dejan margen teórico, no prueban capacidad o gasto. Compartir conexión entre pestañas puede ahorrar, pero no se convierte en dependencia de seguridad o cuota global.

No se adoptan exactly-once de extremo a extremo, history Ably oficial, publish de navegador, presencia como juez, outbox/cola/Redis obligatorios, motor TypeScript, pago o un cuarto servicio. Cambios de transporte/garantía requieren propuesta e impacto/aprobación separados.

## 11. Ejemplos técnicos explicados

Ejemplo documental **PROPUESTA**, sintético y sin conexión a proveedor. El Notice real usa el schema del dueño 05.04, no un DTO paralelo:

```json
{"name":"game.notice.v1","data":{"noticeSchemaVersion":1,"eventId":"g:00000000-0000-4000-8000-000000000201:r:42","gameId":"00000000-0000-4000-8000-000000000201","revision":"42","type":"game.updated","stateSchemaVersion":1,"eventSchemaVersion":1,"rulesVersion":"TK-N1-1.0.0","semanticRange":{"firstSequence":0,"lastSequence":2,"eventCount":3}}}
```

Ese rango indica tres eventos confirmados, sin nombrar piedras o resultado desde el aviso. Secuencia conceptual:

```text
Réplica r40; listener antes de attach; GET inicial en vuelo.
Llegan Notice42, duplicado42 y Notice41 -> objetivo42.
GET devuelve r41 -> instalar r41 y programar lectura acotada pendiente.
Segunda lectura devuelve r43 -> instalar r43; objetivo42 satisfecho.
Respuesta HTTP tardía de comando accepted en r41 -> resolver intención, no retroceder.
Heartbeat responde activityVersion8 y luego llega versión7 -> conservar8.
GET terminal r50 incorpora rematch X versión0; luego X versión1 aceptado.
Otro intent Y versión0 viene de GET posterior -> otra entidad, no regresión a X0.
```

Si faltan eventos de r 42, representar r 43 y último movimiento oficial sin animación incompleta. Al perderse el último Notice 44 sin uno posterior, comprobación acotada/foco/reconexión lee REST. Ninguno de esos GET renueva deadline. Estos casos no afirman una trayectoria legal ejecutada ni orden observado del proveedor.

## 12. Casos límite, fallos y seguridad

| Caso | Conducta / recuperación |
|---|---|
| Commit confirmado y aviso perdido | Snapshot/receipt conservan efecto; checks acotados recuperan, sin outbox supuesto |
| Avisos N+1 antes de N, duplicados o salto | maxTarget y lectura; no ordenar verdad por timestamps/seriales ni aplicar delta del Notice |
| Aviso llega durante attach/GET | Buffer de mayor objetivo; segunda lectura solo si falta, dentro del cap |
| Snapshot menor/igual divergente o epoch antiguo | No retroceder/cruzar principal; divergencia bloqueada y reconsulta segura |
| Misma revisión y actividad nueva/heartbeat tardío | Merge por activityVersion propia; no 304 ni deadline antiguo sobrescrito |
| Rematch cambia sin Notice y contador de intent nuevo 0 | GET terminal serializado/epoch, versión por entidad; polling 06.01 acotado |
| HTTP perdido tras movimiento o commit incierto | Mantener intención exacta/consultar recibo; no rollback supuesto, nuevoID o animación especulativa |
| Falta página/evento o mismoUUID distinto payload | Cancelar/omitir animación, snapshot confirmado y diagnóstico; no fabricar secuencia |
| Ably falla, REST disponible | Estado recuperado por REST con degradación visible y acciones solo tras reconciliar |
| Ably conectado, Game/DB o validación indisponibles | Desconectado/sincronizando del producto; no confirma desde el socket |
| Access expira/Identity caído/capacidad residual | Renovar según dueños cuando disponible; sin permiso nuevo por residual o publicación cliente |
| Rate limit, cuota real agotada o caps locales | Respetar Retry-After/caps y comunicar demora; no upgrade/pago o loop de reconexión |
| Hidden/foco repetido/varias pestañas | Pausar timers, coalescer, revalidar al volver y contar recursos por pestaña; no presencia arbitral |
| Terminal/expired recibido tarde o snapshot pending | Fase/allowedActions Game mandan; no nueva jugada, capacidad terminal o reloj deportivo |

El transporte no identifica exactamente cuándo se desconectó un participante HTTP/serverless. Recuperación 24 h y sus carreras pertenecen a Game/06.03; el estado visual no altera esa cronología. Barreras y permisos actuales se verifican por REST incluso si la capacidad Ably anterior sigue viva. Rewind puede entregar avisos mínimos recientes, nunca autorización de detalle. No exportar secretos/PII al canal o al logging de errores.
